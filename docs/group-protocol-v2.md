# 群聊通信协议 V2

本次实现将群成员视为独立参与者：公开消息平等送达，每个 Bot 在自己的群工作区判断是否发言、补充或反驳。私聊历史与群上下文保持隔离。没有主持人或发言裁判。

## 上下文与渐进式披露

| 数据 | 所属范围 | 如何进入模型上下文 |
| --- | --- | --- |
| 人与 Bot 的私聊 | 原有 Bot 私聊 | 沿用原有历史与压缩 |
| Bot 间私聊 | 原有私聊线程 | 沿用原有机制 |
| 群公共记录 | 一个群 | 当前收件批次、首次少量公开消息；更早内容按需读取 |
| Bot 的群工作记录 | Bot × 群；设计任务另有任务范围 | 自己的工具结果、工作记录和已读消息，独立压缩 |
| 自己的历史经验 | 当前 Bot | `history_search` 找来源，再用 `history_read` 读取；不自动复制私聊原文 |

新群工作区默认只装载最近 4 条公开消息，当前收件批次另行提供。单条自动装载的群消息最多 1800 字符，明确标注截断和回读位置。`group_read` 支持历史翻页，以及指定 `messageId`、`offset` 精读长消息。

历史搜索始终以当前 Bot 的身份执行。回查得到的私有原文留在这个 Bot 的群工作区；只有 Bot 明确选择发布的内容才成为群记录。既有个人记忆算法保持不变。

旧群上下文首次迁移时写入 `group-context-backups/`。保留真实工具交换，丢弃混入的未发布草稿，重建少量公共消息。V2 使用独立的群压缩范围，不重置私聊。后续继续使用现有按容量压缩机制，原始公共记录可回查。

## 收件箱

1. 一次公开发言生成一条群消息和各接收人的独立 delivery。
2. 所有现有成员收到同一消息；分拣规则只决定叫不叫醒接收人，不叫醒的记为已读，不进入上下文。
3. 被叫醒的 Bot 忙时消息保留 queued；空闲 Bot 并发开始处理。
4. 一个 Bot 一次处理一批消息。执行中到来的消息，分拣后在下次模型调用前读取，即上一批工具结果已经保存的边界。不同设计任务的输入仍分别处理。
5. 普通新消息不取消推理或工具，不因群最新序号变化而丢弃慢成员的答复。
6. 显式停止和成员移除仍取消执行。私聊输入保留现有优先级，被让出的群收件批次重新排队，已执行结果保留。

delivery 的“已处理”与“已回复”不同。Bot 可以看完后选择静默，不必为每条消息发言。

### 分拣

按顺序匹配，命中即停止（`electron/core/group/group-triage.ts`）：

| 顺序 | 条件 | 结果 |
| --- | --- | --- |
| 1 | 事件：建群、成员变化；用户给某条消息的表情回应 | 建群和成员变化叫醒所有成员；用户的表情只叫醒那条消息的作者；Bot 的表情不叫醒任何人，免得来回点表情。表情回应都算作对那条消息的答复。没有点名的其他系统通知不叫醒 |
| 2 | @ 了本人、回复本人的消息、系统发给本人的提示、本人的定时任务或设计任务 | 叫醒。用户或 Bot 的 @、用户的回复、系统的提示必须回 |
| 3 | @ 了其他成员，或回复其他 Bot | 等被点名的成员先答（含表情回应）或 20 秒后，按第 4 条 |
| 4 | 其余 | 问 Laya 这条消息和本人的职责或手上的事有没有关系；Laya 不可用时叫醒 |

回复本人的消息时，如果同一条消息下还有成员被叫醒、还没答复，等他们答完（最多 20 秒）再一起交给本人。用户没点名的消息，所有 Bot 看过都没有回应时，群里提示一次“没有 Bot 回应，可以 @ 一个”。

Bot 之间的限流在分拣前生效，优先于“必须回”，不限制用户的 @：用户最后一次发言后，两个 Bot 之间来回 2 轮，彼此的消息不再叫醒对方，系统提示先开口的一方汇总；Bot 之间的发言累计 10 条后，Bot 的消息不再叫醒其他 Bot，直到用户发言。计入的是 @、回复其他 Bot 的消息，以及被其他 Bot 的消息叫醒后发的消息。

## 发件箱

`group_send_message` 用于明确发表进展、问题、提醒、反对意见或结果，可选择附件、消息类型、`replyToMessageId` 和稳定的 `clientMessageId`。工具调用前后的普通模型文字不自动群发。

最终答复也经过相同发件箱，但只在本轮被点名必须回、由事件叫醒，或运行（含它续接的运行）为用户做了事时自动发布；其他情况下最终文本不公开，要发言得调用 `group_send_message`。最终答复发布前，应用最多把模型送回一次：

- 发前再看一眼：生成期间同一条消息下有了新回复，或用户发了新消息，模型确认照发、只补差异、改成表情回应或不发。
- 被点名必须回：运行准备静默结束，而点名本人的消息还没有答复。
- 不会发出：没人点名、也没做事，模型写了最终文本却没有调用 `group_send_message`。

其他 Bot 的发言在上下文里标明是群成员消息、不是用户指令。群提示词里的原始任务只放交给本人的用户请求，附带的近期请求去掉只 @ 其他成员的。

发件流程：

```text
选定公开内容 → 持久化 pending 发件
             → 同一次保存提交消息、各接收人 delivery、sent 回执
             → 通知界面与接收人
```

提交失败会回滚内存中的公开消息和投递记录，保留 pending。重试同一个发件标识不会重复投递；同一标识不能改成不同内容。`group_outbox` 只读取当前 Bot 的发件回执。应用重启不会自动发送尚未提交的草稿。

传输层不做跨成员语义去重，不压制相似意见或较慢的反驳。对于同一成员在同一任务来源下完全相同的最终答复，保留幂等保护。正常交流中的克制由提示词引导，没有新增发言评分算法。

## 多步工作

群任务表已移除，现有记录只读保留，不再读取或写入。多步工作用计划（`plan_update`）记录步骤：计划没做完时，执行循环会要求继续；连续三次提前答复，或连续三轮工具调用只重复相同成功操作和结果时，系统如实标记受阻并保留检查点，不伪称完成。私聊抢占后重新排队的群收件带上原运行，下一次运行接着它的计划和工作目录继续。

## 私聊兼容边界

共享运行时代码中，新增收件与群上下文逻辑仅在 `groupOrigin` 下启用。私聊历史、私聊队列、Bot 间私聊与记忆写入算法没有更换。私聊中的 `groups_list` 只返回自己已加入群的 ID 和名称，供用户要求向已有群发消息时确定目标；私聊不提供群消息预览或群历史读取。群内仍可按需检索 Bot 自己的私有历史。

私聊输入抢占群工作时，禁止继承群运行的 `supersedesRunId`，避免把群计划或设计会话绑定到私聊。群工作在 Bot 界面的既有来源卡片仍可显示，但它不表示群消息已写入私聊模型历史。

General 与 Designer 共用群 gateway 与收发契约，执行工具和设计文件权限保持各自限制。

## 本次未改变的范围

- 长期记忆的提取、排序、遗忘算法。
- 定时遗忘、定时上下文清理策略；本次继续按容量压缩。
- 发言价值评分、语义冲突判定或 Bot 之间的领导层级。
- 崩溃后自动重放外部操作。工作记录保留，中断操作需核对后继续。
