# AI 派对游戏：谁是卧底、你说我猜、故事接龙、海龟汤

状态：方案已确认。第 1–3 步已实现（游戏模式接口、人格对局事实、谁是卧底），第 4–6 步未开始。2026-10-14。

AI 游戏目前只有狼人杀。这次确定新增四个语言类派对游戏：谁是卧底、你说我猜、故事接龙（带卧底）和海龟汤。本文讲三件事：从狼人杀运行时拆出通用的游戏模式接口（第 1 节）；让人格模块对所有游戏通用，使新游戏同样影响好感和人格成长（第 2 节）；四个游戏的规则和 AI 玩法（第 3 节）。范围和关键决定已经确认，见第 6 节，实现按第 5 节的顺序分 PR 进行。

本文不另起一套抽象，沿用两份已有的底座文档：

- [AI 游戏协作底座](ai-game-collaboration.md)：五个概念（共享上下文、参与者上下文、事件、参与者、规则）、一条事件循环、异常处理边界，以及第 5 节的七条约束。
- [AI 游戏模块](ai-game-module.md)：沿用游戏业界的概念名（游戏模式、游戏状态、观察、控制器），以及第 10 节的计划「第一版先迁移狼人杀，再加一个游戏检验通用性」。

本文就是这一步的具体落地。唯一的改动是把检验用的游戏从斗地主换成谁是卧底，原因见 1.3。

## 1. 游戏模式接口

### 1.0 与底座概念的对应

| 底座概念 | 代码里的对应 | 现状 |
| --- | --- | --- |
| 规则 / 游戏模式 | `GameMode`：建局、校验、接受行动、推进、结束 | 只有狼人杀，本文把它拆成接口 |
| 共享上下文 / 游戏状态 | `MatchState` 的公共字段和不带接收范围的日志 | 已有，按狼人杀命名 |
| 参与者上下文 / 观察 | `view(s, viewerId)`，加上 `prompt()` 生成的模型输入 | 已有按座位过滤，提示词是狼人杀专用 |
| 事件 | 日志（带 `audience`）和行动请求（`GameRequest`） | 已有 |
| 参与者 / 控制器 | 座位，加上真人或 AI 两种响应来源；运行时负责调度、超时、重试和暂停 | 已有，和游戏无关 |

运行时已经实现了底座里的事件循环和异常处理，这次不改。需要拆出来的只有「规则」这一格。

### 1.1 现状：哪些是通用的，哪些和狼人杀绑在一起

`GameRuntime` 的大部分逻辑已经和游戏无关：请求排队和并发上限、模型重试与退避、真人倒计时、暂停和恢复、提交前后的快照与回滚、运行记录（trace）、持久化，以及赛后结算的至少一次投递。这部分不用改。

和狼人杀绑在一起的有五处：

| 位置 | 绑定方式 |
| --- | --- |
| 规则 | 运行时直接调用 `werewolf.ts` 的建局、校验、接受行动、视图和日志函数，存储类型就是 `WerewolfState` |
| 类型 | `GameRequest.kind`、`GameRole`、`GamePhase`、胜方（只有狼人和好人两种）都按狼人杀定义；建局只接受 7 人或 12 人 |
| 模型提示 | `model-player.ts` 的系统提示、动作格式提示和上下文结构都是狼人杀专用 |
| 攻略 | `skills.ts` 固定读取 `assets/game-skills/werewolf` |
| 结算和人格 | 好感、高光、开局打法、关键决策和成长观察都按狼人杀的身份和事件计算，见第 2 节；建局界面、行动控件和战报卡片也只认狼人杀 |

### 1.2 接口

每个游戏实现一个游戏模式（GameMode），运行时只通过它访问规则：

```ts
interface GameMode<S extends MatchState> {
  id: 'werewolf' | 'undercover' | 'charades' | 'story' | 'turtle_soup';
  seats: { min: number; max: number };
  create(input: { groupId: string; players: GamePlayer[]; options: unknown; seed: number }): S;
  validate(s: S, request: GameRequest, action: GameAction): void;
  accept(s: S, requestId: string, action: GameAction, timeout?: boolean): void;
  view(s: S, viewerId?: string, omniscient?: boolean): GameView;
  /** 发给模型的系统提示和局面输入；只能读 view 给出的信息。 */
  prompt(view: GameView, request: GameRequest): { instruction: string; input: string };
  /** 赛后发到群里的战报，不涉及人格结算的游戏只实现这一项。 */
  report?(s: S): string | undefined;
}
```

`MatchState` 是各游戏共用的字段：`id`、`groupId`、`mode`、`status`、`phase`、`round`、`seats`、`logs`、`requests`、`accepted`、`trace`、`revision`、`seed`、`notes` 和结算回执。各游戏的私有状态放在自己的字段里，如谁是卧底的词对、海龟汤的汤底。

- 运行时按 `s.mode` 取游戏模式。旧存档没有 `mode` 字段，读档时补成 `werewolf`，所以不需要迁移文件。
- `GameRequest.kind` 改为各游戏声明自己的动作种类，动作格式（action contract）也由游戏模式提供。纯文字类动作（描述、猜词、续写、提问）共用现有的 `text` 契约，投票共用现有的 `target`/`skip` 契约。
- `GameView` 增加 `mode` 和一个按游戏区分的 `table` 字段，用来放这名观察者能看到的私有信息，比如自己的词。前端按 `mode` 选择牌桌组件。
- 游戏模式还要向人格模块提供几项信息：开局打法表、哪些请求是关键决策、强情境判断，以及对局结束时的通用事实。具体见第 2 节。

### 1.3 用谁是卧底检验接口

谁是卧底的流程是「依次发言 → 同时投票 → 出局 → 判断胜负」，和狼人杀白天的发言、投票几乎一样，能复用狼人杀已有的发言控件、投票控件和超时规则。它同时引入了狼人杀没有的两样东西：每人拿到的信息不同（自己的词），以及动作内容需要规则校验（描述里不能出现自己的词）。用它检验接口，范围小，又能覆盖通用性的关键点。斗地主需要手牌、组合出牌和多局计分三套新机制，适合放在派对游戏之后。

## 2. 人格接入

新游戏和狼人杀一样，会影响 Bot 的好感和人格成长。人格模块的核心本来就和具体游戏无关：五维人格、好感、在合理候选里按人格抽样、跨局成长评估。和狼人杀绑在一起的，只是它从对局里读取信息的方式。

所以改法是让人格模块只认通用的对局事实，由每个游戏模式把自己的规则翻译成这些事实。判断标准是：以后某个游戏如果需要人格模块为它写特例，就说明通用事实的定义还不够，应该修改事实的定义，而不是加特例。

### 2.1 人格模块和对局的接触点

下表按 [AI 人格模块](ai-personality-module.md) 第 9 节和附录 D.11、D.12 的现状整理。

| 接触点 | 现在和狼人杀绑在哪 | 改成 |
| --- | --- | --- |
| 开局打法 | 打法表只有狼人、预言家、女巫、村民四种身份；「上次用过的打法」也按这四种身份记 | 打法表由游戏模式提供，可以为空；「上次用过的打法」按「游戏:身份」记 |
| 人格片段 | 已经通用，只依赖五维人格 | 各游戏的提示词带上同一段说话风格和本局打法 |
| 关键决策 | 关键决策的种类是狼人杀的固定列表；强情境规则是「只有一个合法目标」和「预言家查到的狼」 | 由游戏模式声明哪些请求是关键决策，并提供强情境判断；候选、语义和引用核验逻辑不变 |
| 好感和高光 | 阵营只有狼人和好人两种；事件只有放逐和女巫解药 | 游戏模式在对局结束时给出通用事实（2.2），人格模块按事实计算 |
| 成长观察 | 解析模型输入时依赖狼人杀字段（身份、女巫信息）；观察里的身份是狼人杀身份类型 | 所有游戏的模型输入使用同一个外层结构：本人、共享上下文、个人上下文、行动请求；身份改为「游戏:身份」字符串 |
| 跨局成长评估 | 评估提示里的反例都是狼人杀的，如「狼人欺骗不等于低宜人性」；要求证据跨两种身份 | 反例改成通用说法，如「角色任务要求的欺骗」「规则强制的发言」，游戏模式可以补充本游戏的反例；「跨两种身份」改为「跨两种 游戏:身份」 |

说话风格对所有文字行动都生效，包括描述、提示、续写和提问。这是人格在派对游戏里最主要的表现，成长观察也会采集这些发言。

### 2.2 对局结束时的通用事实

游戏模式在对局结束时交给人格模块四样东西：

- 队伍：每个座位属于哪一队。没有队伍的游戏每人自成一队；合作游戏全员一队。
- 结果：哪些队伍获胜。手动结束的对局没有结果，不结算，这条沿用现有规则。
- 社交事件：两名玩家之间、由规则确认的事。第一版有三种：
  - 同队相投：A 投票让同队的 B 出局。只写进 B 的高光，不自动减好感。这沿用 D.11 的结论：这样的投票可能是战术，也可能是误判，不能当成怨恨。
  - 相助：A 的行动直接帮到了 B。B 对 A 的好感 +0.3，持续 30 天，数值沿用女巫救人。
  - 同队获胜：队友之间好感 +0.1，持续 14 天，沿用现有规则。
- 关键事件：一句话描述，用于战报和高光。

同一局里，同一对玩家的同一种社交事件只记一次。否则在你说我猜里，同一对玩家反复猜中就能把好感刷满。

狼人杀的翻译方式：被同阵营放逐对应同队相投，女巫解药对应相助，阵营对应队伍。翻译后的结算结果必须与现在完全一致，用现有的结算测试保证。

### 2.3 四个新游戏的人格表现

| 游戏 | 队伍 | 关键决策 | 相助 | 开局打法 |
| --- | --- | --- | --- | --- |
| 谁是卧底 | 平民一队，卧底一队，白板单独一队 | 投票 | 无 | 两种：直白描述、模糊描述 |
| 你说我猜 | 每人一队 | 无 | 描述者的提示让某人猜中：描述者帮了猜中者 | 无 |
| 故事接龙 | 作者一队，卧底一队 | 最后的投票 | 无 | 卧底两种：尽早埋词、最后一圈埋词 |
| 海龟汤 | 全员一队 | 无 | 无 | 无 |

- 谁是卧底的打法不按身份区分，因为玩家开局不知道自己是不是卧底。
- 打法的行为特征沿用人格模块第 9.2 节的标注方式：直白描述、尽早埋词标为高风险、高主张；模糊描述、最后埋词则相反。这些标注和狼人杀打法表一样，是待校准的工程假设。
- 海龟汤的 AI 主持不是座位，不参与好感和成长。

## 3. 四个游戏的规则

四个游戏都是回合制，没有抢答和实时操作。「抢答」用「同一轮所有人同时提交，一起揭晓」代替，这样真人和 AI 的响应速度差异不影响胜负。

### 3.1 谁是卧底

**人数和身份**：4–10 人。4–6 人 1 名卧底，7–10 人 2 名卧底；7 人以上可选加 1 名白板。平民拿到同一个词，卧底拿到相近的另一个词（如 牛奶 / 豆浆），白板没有词。**卧底不知道自己是卧底**，每个人只知道自己的词。

**流程**：

1. 描述：存活玩家依次各说一句描述，每轮起始玩家顺延一位。每句 1–60 字，不能包含自己的词。
2. 投票：所有存活玩家同时投票，可以弃票。得票最多者出局，并公布身份（平民、卧底或白板），不公布词。
3. 平票：平票的几人各补充一句描述，其他人在他们之中重投一次；再平票本轮无人出局。

**胜负**：卧底和白板全部出局，平民胜。存活的卧底人数不少于存活的平民，或只剩 3 人时仍有卧底存活，卧底胜。白板出局时可以猜一次平民的词，猜中则白板单独获胜。

**校验**：描述中出现自己的词（忽略空格、标点和大小写）时拒绝。AI 收到拒绝原因后重试，真人在界面上看到提示后修改。拼音、谐音和拆字第一版不检查。

**AI 的玩法**：AI 要从别人的描述推断自己可能是卧底，然后改用两个词都符合的描述来隐藏。提示词会说明这一点，但不告诉它身份。决策备注（note）会记录它对自己身份的判断，赛后在复盘里展示，这是这个游戏的看点。

### 3.2 你说我猜

**人数**：3–8 人。每人轮流当一次描述者，其余人是猜词者。

**一回合的流程**：

1. 描述者拿到一个词，给出一条提示，1–40 字，不能包含词里的任何一个字。
2. 所有猜词者同时提交一个猜测，或者跳过。
3. 揭晓本轮所有猜测。有人猜中则回合结束；没人猜中则描述者再给一条提示，最多 3 条。

**计分**：第 1、2、3 条提示后猜中，猜中者分别得 3、2、1 分；描述者每有一人猜中得 1 分。全部回合结束后总分最高者获胜，同分并列。

**判定**：猜测去掉空格和标点、统一全半角和大小写后，与词或词库里登记的同义说法完全一致才算猜中。第一版不用模型判定，以免同一个猜测在不同对局里判法不一样。

**信息边界**：词只有描述者看得到；猜测在本轮揭晓前互相不可见，防止跟猜。

### 3.3 故事接龙（带卧底）

**人数和身份**：4–8 人。开局随机抽一名卧底，私下给他一个秘密关键词（如「香蕉」「雨伞」），其余人是作者。所有人都看到同一个故事开头。

**流程**：

1. 按座位顺序轮流续写，每人每次一句，1–80 字，共 3 圈。
2. 3 圈后所有人同时投票，指认卧底。

**胜负**：卧底本人写出的句子里出现过秘密关键词，并且没有被投出，卧底胜；否则作者胜。别人碰巧写出关键词不算。投票平票时卧底算未被投出。作者可以故意写一些突兀的词来干扰判断。

**战报**：赛后把完整故事和卧底的关键词一起发到群里。这个游戏的产出本身就值得分享。

**第一版不做**：「让主角失忆」这类情节任务需要模型判断是否完成，判断结果不稳定，第一版只用关键词任务。

### 3.4 海龟汤

**角色**：1–8 名玩家，加一名主持。主持由 AI 担任，不占座位，能看到汤底和关键点，其他人看不到。第一版不支持真人当主持。

**题目**：每道题包含汤面（公开）、汤底（只有主持知道）和 3–5 个关键点。还原的判定标准是关键点，而不是汤底的原文。

**流程**：

1. 玩家按座位顺序轮流行动，每次可以提一个是非问题，或者提交一次还原。
2. 主持回答提问，只能从「是」「不是」「无关」「是也不是」中选一个，并可以把问题标记为「关键问题」。主持不写自由文本，以免说漏汤底。
3. 主持判断还原覆盖了哪些关键点，只公布命中的数量，不公布是哪几个。

**结束**：所有关键点被不同还原累计命中，玩家胜；全队共 30 次提问用完仍未还原，公布汤底。这是合作游戏，战报按提出关键问题和命中关键点的次数给出本局最佳玩家。

**主持的风险**：主持回答错误会把玩家引向错误方向。降低风险的做法是让主持每次回答时同时看到汤底和关键点，并在 note 里写一句依据，赛后复盘可以检查。要不要加第二个模型复核回答，等试玩后再定。

**AI 玩家**：AI 只能看到汤面和问答记录，游戏里没有搜索工具，无法上网查答案。

## 4. 内容、界面和测试

### 4.1 题库

每个游戏的内容放在 `assets/game-content/<mode>/`，用 JSON 存储，和攻略文件一样按内容哈希记版本，运行记录里记下这局用的版本。抽题用对局种子，同一种子可以重放。每个群记录最近用过的题，避免短时间内重复出题。

| 游戏 | 第一版内容 | 每条包含 |
| --- | --- | --- |
| 谁是卧底 | 约 150 对词 | 平民词、卧底词、分类 |
| 你说我猜 | 约 300 个词 | 词、同义说法、分类、难度 |
| 故事接龙 | 约 30 个开头、100 个关键词 | 开头文本；关键词 |
| 海龟汤 | 约 20 道原创题 | 汤面、汤底、关键点 |

初版内容由我编写，你审核后入库。网上流传的海龟汤大多来源不清楚，第一版只用原创题。以后可以让 Bot 以作者身份出题，按 [AI 游戏模块](ai-game-module.md) 第 9 节的流程审核后上架。

### 4.2 界面

- 建局：先选游戏，再选玩家。每个游戏卡片显示人数范围和一句规则说明；谁是卧底多一个「加白板」开关。
- 牌桌：座位列表、对局记录、倒计时和暂停/结束控件沿用现有组件。各游戏只增加自己的信息区，比如自己的词、当前故事全文、问答记录和剩余提问次数。
- 行动：描述、猜词、续写和提问都使用现有的文字输入框，投票使用现有的投票控件。海龟汤的「提问 / 还原」用一个切换按钮区分。
- 战报卡片：按游戏显示胜负和一两项亮点。

### 4.3 测试

验收沿用 [AI 游戏协作底座](ai-game-collaboration.md) 第 5 节的七条约束，新游戏主要考验其中两条：

- 信息有界：谁是卧底的词、海龟汤的汤底和关键点、故事接龙卧底的关键词，都不能进入其他座位的观察、模型输入和对局记录。测试直接检查每个座位的 `view` 和 `prompt` 输出。
- 决策时点一致：你说我猜的猜词、各游戏的投票都是同时提交，揭晓前互相不可见，AI 回复得快也看不到别人的答案。

每个游戏都照狼人杀现有的方式写测试：用随机的合法玩家跑完整局，确认每一步都有合法行动、能正常结束、同一种子可以重放；再针对平票、白板猜词、描述含词被拒、海龟汤次数耗尽等边界各写用例。拆分接口的 PR 要求现有狼人杀测试全部通过、断言不改。

## 5. 实施顺序

| 步骤 | 内容 | 验收 |
| --- | --- | --- |
| 1 | 拆出游戏模式接口，狼人杀迁成第一个游戏模式 | 狼人杀行为不变，现有测试全部通过；旧存档能正常读取 |
| 2 | 人格模块改为读取通用事实（第 2 节），狼人杀提供翻译 | 狼人杀的好感、高光、成长观察结果与改动前完全一致；旧的成长观察和人格档案能正常读取 |
| 3 | 谁是卧底、建局时选择游戏、第一批词库 | 能和 AI 打完整局；战报回群，好感和成长观察正确记录 |
| 4 | 你说我猜 | 多回合计分正确，猜词判定稳定；相助事件每局每对只记一次 |
| 5 | 故事接龙 | 完整故事和卧底揭晓进入战报 |
| 6 | 海龟汤：AI 主持、题库 | 主持只用规定的四种回答，还原判定可以在复盘里核对 |

每一步一个 PR。第 1、2 步只做重构、不加功能，方便评审时确认狼人杀和人格模块没有被改坏。

## 6. 决策记录

2026-10-14 已确认：

1. 人数：谁是卧底 4–10 人，你说我猜 3–8 人，故事接龙 4–8 人，海龟汤 1–8 名玩家加 AI 主持。
2. 新游戏影响 Bot 的好感和人格成长。如果接入时发现人格模块必须为某个游戏写特例，说明人格模块的抽象不够通用，应该修改人格模块，而不是绕过它。
3. 海龟汤的主持默认用群里第一个 Bot 的模型，建局时可以改。
4. 题库由我编写初版，审核后入库。
