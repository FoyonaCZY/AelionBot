# 长任务缓存复用：二次源码对照

日期：2026-09-10。对照基线为当前工作区（包含尚未发布的校准倍率、持久裁剪和计划恢复修复），不是仅对照已发布的 v0.14.2。

最初调查没有修改生产逻辑。随后用户要求“全部优化”，本报告列出的客户端改进现已实现于工作区，详见 `Prompt-Caching.md`。没有调用真实收费模型、重启客户端或发布版本。

## 结论

还有明确的优化空间。已修正的倍率重复放大、裁剪视图反复展开属于必要修复；它们不代表请求历史已经稳定到可以整体增量复用。

优先顺序：固定消息序列和参考快照；用实际用量锚定容量决策；减少多次小规模历史改写；最后按供应商能力优化传输。不能仅靠增加缓存参数或保留更多无用文本来追求命中率。

## 1. 动态状态放在尾部，但没有保留在原位置

Aelion `ContextEngine.prepare` 每次重新构造 `history + controls()`，controls 包括任务状态、运行上下文和计划。controls 并未成为持久的模型可见历史。

例子：第一次发 `历史 → 状态 A`，收到回复后，下一次发 `历史 → 回复 → 工具结果 → 状态 B`。原来的状态 A 消失了，即便 B 与 A 相同也会挪位置。因此新的请求不是 `上次请求 + 上次输出 + 新输入`。

[Codex 的 get_incremental_items](https://github.com/openai/codex/blob/main/codex-rs/core/src/client.rs) 明确用“前次 input 与服务端返回 output 的拼接”检查当前请求前缀，其他请求字段也必须兼容，才发送增量。这是比仅将动态内容移到尾部更严格的约束。其 WebSocket 实现依赖服务端支持，不能直接当作 MiMo 通用能力。

建议：单独保存模型可见的上下文事件；状态仅在发生变化时追加；已经发送的事件留在其原位置，不在每轮重复注入完整状态。原始用户对话、UI 展示和模型输入可以有不同视图。最新授权继续由执行层检查，旧状态不能恢复已撤销的权限。压缩时再合并这些事件。

收益边界：目前历史主体通常仍稳定，不能把尾部移动解释成每次全量缓存失效；但它妨碍上次完整请求及生成结果的前缀复用。

## 2. 参考快照仍可能在历史前部变化

`harness.ts` 每次新运行重新生成记忆、技能目录及环境参考，并放在历史之前。`ContextEngine.loadedSkills` 在发生过压缩后，每次 prepare 都从最近技能读取记录重新选取参考正文，仍插在保留的历史之前。后者可能在同一次长任务中改变靠前的输入。

[Hermes 的 prompt assembly](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/developer-guide/prompt-assembly.md) 区分缓存的系统提示与临时补充，并使用会话快照；文档还明确描述某些界面切换通过一次性的消息补充传达，而保留原有提示字节。它仍有 ephemeral 层，不能声称 Hermes 的所有路径都是严格追加。

建议：以会话/压缩周期保存参考快照；普通记忆与技能更新用有版本的增量事件通知，压缩时重建基础快照。不要冻结热更新或权限执行检查。工作目录、用户规则、模型或工具集的真实变化应明确处理，允许必要的缓存失效。

## 3. 容量决策仍过度依赖全量估算和固定比例

Aelion 先从窗口减去输出预算与安全预留，再以剩余输入预算的 85% 触发裁剪/压缩。离线计算：128,000 窗口在 98,355（约 76.8%）触发，256,000 窗口在 207,155（约 80.9%）触发；1,000,000 窗口在 839,555（约 84.0%）触发。新校准已经修复重复放大，但尚未改变这个决策方式。

[OpenCode 的 overflow.ts](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/session/overflow.ts) 以实际记录的 token 使用量检查可用窗口，同时根据模型的输入/上下文/输出限制预留空间。[其 compaction.ts](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/session/compaction.ts) 还保留近期工具输出，并设置最小裁剪收益；完成的裁剪有持久标记。它同样会裁剪，不应照搬成“永不改历史”。

建议：以同一模型、同一发送视图最近成功请求的实际输入用量为锚点，加上新消息、工具结果、输出与图像的增量估计。模型切换、历史改写或缺失用量时退回安全估计。将容量风险与是否值得破坏缓存分别决策；需要裁剪时一次释放足够空间，避免连续少量改写。不能照抄其他项目的 token 加法，Aelion 各协议已经有自己的输入/缓存归一化语义。

## 4. 图像存在独立的滑动淘汰

`src/model-images.ts` 只保留最后两张截图和最后十个附件图像。协议转换每次按最新集合过滤旧消息，因此新截图会改变较早消息，即便文本裁剪视图完全稳定。

离线调用真实协议转换确认：加入第三张截图，原第一张截图所在消息由图文变成纯文字。

建议：让图像生命周期进入统一的容量与裁剪决策，在明确的周期边界批量归档，并保留可回查引用；不能简单无限保留图像。该项影响桌面/多图任务，不能用来解释没有图像的纯代码长任务。

## 5. 传输优化与诊断

Codex 有会话级连接状态、回合路由状态和条件性的 Responses WebSocket 增量传输。Aelion 已有稳定缓存 key、会话提示头和原生推理回传，但仍通过 HTTP 发送完整输入。仅发送提示头不能保证第三方网关真的提供粘性路由。

建议：对支持的服务端再实现增量协议和断线回退，保留完整本地历史用于恢复；不要给所有兼容接口强塞 previous_response_id 或改变 store 语义。增量上传字节减少不等于计费缓存必然提高。

诊断应进一步区分：参考快照变化、状态挪动、图像淘汰、正文裁剪、摘要重建、真实工具变化和服务端未知因素。当前只比较前次发送请求的哈希，无法给出“前次成功输入 + 已返回输出”可复用前缀的精确覆盖率。增加这项可帮助区分客户端损失与服务端未命中，但字节匹配仍不是供应商 token 缓存计量。

## 离线验证

可复现脚本：`.local/cache-comparison-probe.ts`；结果：`.local/cache-comparison-probe.json`。使用独立临时 Store/CognitiveStore 和真实 ContextEngine/protocolRequest；禁止模型调用，结束清理临时数据。

- 追加消息后，前次尾部控制消息的位置从 system 变为 assistant；不是严格追加。
- 修改参考快照后，第 2 条输入发生变化。
- 第 3 张截图使第 1 张截图所在的旧消息变化。
- 计算三个窗口大小的实际触发阈值。

以上验证的是客户端输入行为，没有测得这些改动能带来多少百分点提升，也没有与另一个 agent 在相同 provider、账号、任务和时段做收费 API A/B 对照。验收应同时观察任务正确性、实际缓存读取/总输入、未缓存 token 总量、压缩次数和耗时，而不能靠重复冗余输入抬高命中率。

## 后续实现

- `context-view.ts`：跨请求/重启保持状态事件位置；参考资料增量更新；按消息中的图像出现位置批量归档。
- `context-meter.ts`：使用实际用量锚点，新增内容才估算；避免将锚点再次用于学习倍率。
- `context-engine.ts` / `harness.ts`：主会话、私聊和群聊统一上下文管理，保留实时权限及知识更新；减少小收益裁剪。
- `responses-transport.ts`：有界连接池、严格前缀校验、WebSocket 增量、完整 HTTP 回退、取消/关闭清理。Provider 可选择连接方式。
- `prompt-cache.ts` / diagnostics：分别记录逻辑完整输入与传输增量，并对照成功输入和输出的前缀。

新增回归覆盖消息顺序、参考更新/撤回、重启、跨 scope 隔离、实际用量估算、图像重读、归档、旧响应 ID 失效、连接中断、取消和不支持 WebSocket 的接口。最初 `.local/cache-comparison-probe.ts` 是旧行为复现材料；实现后的正确行为以 `tests/context-view.test.ts`、`tests/responses-transport.test.ts` 和更新后的已有回归为准。
