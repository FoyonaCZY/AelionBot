# GrokBot 实机观察与首版交互方案

> 0.2 交互修订：按用户后续要求，右侧只保留电脑，技能和记忆进入设置；产物采用聊天内文件卡片和居中预览。下文原有“成果/电脑/计划”右栏提案属于历史方案，已被此决定替换。

2026-09-05 补充：经用户明确授权，在 GrokBot 中生成了合成的 `report.md`（254 B）和 `sample.csv`（26 B），实际观察了文件名/大小/独立保存按钮的聊天卡片，以及带文件名、下载和关闭按钮的居中报告预览。两个测试文件保留。AelionBot 0.2 按这一交互结构实现，未复制 GrokBot 源码和品牌素材。

日期：2026-09-05。观察对象：用户本机已打开的 Grok Bot Windows 应用，中文界面。版本号未核实。

本次实际浏览了现有 Bot 会话、对话详情、Bot 资料、群聊收件人草稿、电脑预览与全屏、例行任务编辑与触发器菜单、插件/Bot 市场和新建 Bot 引导。下文把直接观察与我们的设计建议分开；未测试多人协作的真实执行、工具可靠性、后台恢复、完整文档产物或训练示范。

体验时“创建新 Bot”立即创建了一个默认名称的 Bot，并自动出现用途问题卡；未给它下达业务任务，随后使用“从侧边栏隐藏”将它隐藏，未删除。原 Bot 的任务、连接器与设置未修改；没有新增带触发器的例行任务，没有安装插件、公开分享或发送对外消息。回到原 Bot 会话并恢复原窗口大小。未把用户聊天正文、账户资料或原始截图保存进工作区。

## 1. 实际观察

| 编号 | 界面与操作 | 直接看到的行为 | 对本产品的启发 |
|---|---|---|---|
| O1 | Bot 主会话 | 左侧是头像、名字、时间和最近消息摘要；中间是消息气泡；系统动作以较轻的行内事件呈现 | 用“可联系的同事”组织入口；任务细节按需展开 |
| O2 | 新建聊天 → 收件人 | 同一个搜索/创建入口提供创建新 Bot、创建群聊和现有 Bot | 一个新建入口承载不同协作规模，降低入口数量 |
| O3 | 群聊草稿 → 选中 Bot | 收件人变成可移除的 chip，输入框文案随参与者变化 | 成员选择直接可见；我们的房间再增加共同目标和交付约定 |
| O4 | Bot 详情 | 右侧有电脑缩略预览、Bot 的屏幕名称、例行任务入口和设置 | 把电脑作为工作的辅助面板，不做虚拟机管理中心 |
| O5 | Bot 设置 | 头像、名称、标签、用途描述、完成/需要回复时通知的开关 | 角色配置短而可理解；权限和资源配置另行按需展示 |
| O6 | 打开电脑 | 展开为完整桌面视图，可退出全屏；有“教它做一项任务”入口 | 缩略观察 → 展开操作；教学属于后续可探索能力，本次只观察到入口 |
| O7 | 创建例行任务 | 编辑位于右侧：名称、指令、启用状态、测试运行、触发器、运行历史；空白内容的测试运行禁用 | 定时工作沿用 Bot 当前上下文；提供“先试运行，再启用” |
| O8 | 添加触发器 | 可见定时、Slack、Git、Teams、Linear、Sentry、PagerDuty、Webhook 等入口 | 可以复用“何时做”与“做什么”分离的表达；我们首版仅做可本地运行的触发器 |
| O9 | 市场 | 插件与 Bot 分为两类；插件按工作场景分类，Bot 有角色卡片、创建者及搜索 | 用户先选工作结果，再理解技术工具；本产品首版用内置模板和已安装能力列表 |
| O10 | 创建新 Bot | 无需先填写复杂配置，Bot 自动打招呼并询问用途；问题包含选项、自由输入和忽略 | 通过对话渐进建立角色，同时把重要授权留给明确的产品控件 |
| O11 | Bot 右键菜单 | 包含置顶、分组、未读、编辑资料、创建副本、隐藏与删除 | 隐藏和删除分开；创建副本需要明确复制哪些角色资料与哪些私有数据 |

GrokBot 本身已经有群聊入口，不能把“多个 Bot 放在一个聊天里”作为我们的独创差异。本次没有真正建立多 Bot 协作任务，因此也不能从群聊入口推断其任务编排、消息可靠性或权限实现。

现有会话中能看到提问卡和本机操作授权事件，但没有执行新的授权流程。不能据此推断它全部的权限选项，也不能把历史 Bot 消息中的能力描述当作经测试的能力证明。

## 2. 推荐保留的交互思路

### 对话是入口，工作状态始终可定位

保留联系人式 Bot 列表和消息交互。用户可以直接说“把这些资料整理成报告”，无需先创建任务表单。但任务开始后，生成轻量工作卡，固定链接到目标、当前步骤、执行位置和产物。

聊天里显示“正在整理数据”“已交给开发 Bot”“需要你确认附件”之类事件。完整日志、工具参数和环境诊断折叠到详情。普通用户看到工作语言，开发者仍能追溯每一次操作。

### 创建角色采用简短问题卡

初始只需要名字或用途。先让用户决定工作方向，然后在真实需要时选择文件、账号和执行位置。问题卡支持选项、自由输入、跳过和后续修改。

岗位描述和授权分开。选择“代码助手”不自动获得本机 shell，选择“行政助手”不自动获得发送邮件能力。避免聊天式引导把用户对用途的回答误当成权限授予。

### 固定 VM 使用“工作电脑”这一产品概念

用户始终只看到：

```text
工作电脑                  我的电脑
应用准备的独立环境         用户当前的 Windows
运行中 · 开发 Bot 正在用   仅允许文档 Bot 操作 Excel
[查看] [暂停]             [授权范围] [接管]
```

工作电脑由应用创建和维护唯一实例。没有创建 VM、克隆镜像、选择网卡、填 CPU/RAM 或导入 ISO 的入口。底层保留 Bot/Computer 多对多：一个 Bot 可使用工作电脑和本机，多个 Bot 共用工作电脑。

任务涉及完整桌面时显示当前控制者；排队时说明正在等待哪项资源，例如“等待研究 Bot 释放浏览器”。不能把排队伪装成模型仍在思考。

### 电脑预览和成果预览并列

右侧面板提供“成果 / 电脑 / 计划”。多数办公任务默认打开成果；只有桌面操作、登录接管或排障时打开电脑。缩略图显示执行位置、正在控制的 Bot 和观测时间，避免把陈旧画面误认为实时状态。

代码任务自动选择 diff、测试结果和运行预览；文档任务选择可编辑文件及页图预览。打开文件、定位来源、查看版本和导出都在产物卡上完成。

## 3. 协作房间的具体形态

房间采用工作讨论的形式，同时拥有结构化的共同目标。首版新建只需房间名、参与 Bot 和一句话目标，其余按需补充。

```text
侧栏                      协作房间：季度分析                    工作面板
待我处理 2                目标：报告与计算脚本通过审核             成果 | 电脑 | 计划
                          研究 · 文档 · 开发 · 审核
Bot
  研究                    研究：资料已整理，附来源笔记             季度分析.xlsx  v3
  文档                    [研究笔记] [交给文档]                   关键数字核对通过
  开发
  审核                    文档 → 开发：请修正汇总公式              汇总脚本.patch
                          [子任务：修正汇总，进行中]              相关测试通过
协作房间
  季度分析                开发：补丁已提交给审核                   工作电脑
                          [补丁] [测试记录]                       文档 Bot 正在使用
                          ...
                          @研究 @文档 继续...
```

固定三个可追踪对象：共同目标、任务责任人、下一交付。讨论不自动转换为任务；明确的指派或“转为任务”操作才创建 Task。Bot 可以点对点交流，相关任务里的关键交接事件自动回到房间，不要求所有完整私聊都公开。

消息中的任务卡带负责人、状态、预算范围、输入和输出引用。接收方先显示“已接手”或“等待电脑”，完成后交付产物版本。房间顶部汇总目标是否满足，而不是简单显示最后一个 Bot 已回复。

通知按房间聚合：用户需要处理一个审批集合或查看一份最终结果，不需要接收十几条 Bot 互相交流的弹窗。共享电脑时，右侧统一显示当前占用和队列。

## 4. 首版关键状态与文案

| 状态 | 用户应该看到什么 | 能采取的动作 |
|---|---|---|
| 工作电脑未准备 | 准备工作电脑、下载/验证/初始化分阶段进度和空间需求 | 开始准备、查看检测结果 |
| 工作电脑已关闭 | 说明数据保留，下一次任务按需启动 | 启动、查看占用 |
| 任务正常执行 | 当前 Bot、阶段、执行位置和可验证进度 | 补充要求、暂停 |
| 等待共享资源 | 等待哪个 Bot 的哪项资源，不展示虚假思考动画 | 查看队列、调整优先级 |
| 需要本机能力 | 具体应用、文件和目的，以及持续/单次范围 | 授权、继续在工作电脑、拒绝 |
| 用户接管 | 明确“由你控制”，暂停后续输入并保留其他后台任务 | 交还控制、停止任务 |
| 需要决策 | 问题卡、推荐项、自由回答和已有上下文 | 回答、跳过、修改目标 |
| 等待批准 | 将提交的准确内容、账号和目标 | 批准此次、按明确范围授权、拒绝 |
| 完成 | 产物、验证结果、来源和已知限制 | 打开、修改、导出、保存为例行任务 |
| 环境故障 | 分开报告模型连接、guest 联网、资源或执行问题 | 诊断、重试、在安全检查点修复 |

“准备完成”“任务完成”“验证通过”分别由环境、任务和检查事件驱动；不能根据模型一句话改变产品状态。

## 5. 首版应简化的功能

- 市场先简化为四个岗位模板、几个工作模板和已安装连接器；不复制完整公开市场。
- 例行任务先支持时间计划、手动触发和指定目录/本地仓库变化；外部 Webhook 不进入首版。
- “教它做任务”先降为“把这次成功流程保存为技能/例行任务”。录屏学习需要单独验证，不以一个按钮承诺通用复现。
- VM 只保留唯一工作电脑和必要诊断；取消自建电脑、镜像市场和多 Provider 选择界面。
- 群聊保留直接交流，但工作房间突出目标、责任人和产物；避免不断扩展社交功能。
- 隐藏、删除、复制有明确区别。复制角色默认只复制岗位设置和技能引用，不复制聊天、账号、电脑数据或私有记忆。

## 6. 与原详细设计的收敛

本次决策已经写回 0.3 版详细设计与领域契约：首版固定一个受管 VM 槽位，Computer 注册属于应用内部能力，用户及 Bot 不具备通用建机权限。主架构保留多对多模型，部署范围收敛为两个执行位置。

同 VM 的独立 Workspace、进程身份和浏览器会话可以分开工作状态及受支持的访问权限，但仍共享 guest 内核。需要独立 VM 的强隔离不在首版承诺中。整机修复会影响所有 Bot，因此必须有生命周期互斥、检查点、数据保留和影响预览。

UI 的首个可点击原型应覆盖五条路径：创建 Bot 的简短引导；建立带目标的协作房间；房间内委派并交接产物；共享工作电脑排队与本机接管；从已验证成果生成例行任务草案。

这些是根据本次实机观察提出的产品方案，尚未实现为可运行 UI。没有执行性能基准，也没有验证 GrokBot 内部 Harness 或虚拟化实现。
