# 群聊协作方案

状态：方案讨论，尚未实现。相关文档：[群聊通信协议 V2](../group-protocol-v2.md)、[本地 Laya 群聊决策实验](../laya-local.md)。

本版的决定：

- 只有一种协作方式，不设模式。
- 没点名本人的消息，由 Laya 决定回不回。
- 同时开口。
- 不使用群任务。
- 群公告照 Telegram 做：群简介加置顶消息。
- 不改运行调度：每个 Bot 同一时间仍只有一个运行（pi 的做法）；忙碌时用顺带答复（借 Claude Code 的 /btw）。

## 一、目标与前提

目标：群聊接近真人工作群。Bot 先做好用户交给自己的事，同时可以随时参与讨论：对其他成员的工作提建议或反对，也可以发布自己的进展和疑问，征求其他成员的意见。讨论不进入与它无关的上下文。

前提：

- 每个群 3–5 个 Bot。
- 意见可以改变 Bot 的后续做法，但不取消正在进行的推理或工具。
- Bot 之间的讨论都显示在群里。
- @ 指定由谁答复、由谁做；其他成员照常收到，可以发言，不抢着做。
- Laya 是小的决策模型，只做简单判断。
- 沿用 V2 的原则：公开消息平等送达，没有主持人；传输层不做跨成员语义去重；其他 Bot 的发言不构成授权。

## 二、参考

| 来源 | 做法 | 用在 |
| --- | --- | --- |
| pi | 一个 Agent 一个循环。运行中的新输入只有两个去处：当前这批工具跑完后并入（steer），或等运行结束（followUp） | 不改调度（第五节） |
| Claude Code | /btw：根据当前对话回答，不带工具，问答不写入历史，不打断当前这一轮 | 忙碌时的顺带答复（5.2） |
| Claude Code | 其他 Agent 发来的消息标明来源，不能替用户授权 | 上下文（第十一节） |
| Telegram | Bot 默认开启隐私模式，在群里只收到点名它的命令、回复它的消息等，以及系统消息；关掉后像普通成员一样收到所有消息 | 谁回应（4.1） |
| Telegram | Bot 默认看不到其他 Bot 的消息；开启 Bot 之间对话后，被用命令点名或被直接回复时能收到。开启后要自己防循环，建议去重、限速、按每对 Bot 和全局限制往来深度或时长 | 限流（第十三节） |
| Telegram | 没有单独的群公告：群资料里有群简介，公告就是置顶的消息，可以置顶多条 | 群简介和置顶（第十二节） |

没有采用 Claude Code 团队的负责人和共用任务表，它和“没有主持人、不用群任务”冲突。

## 三、现状问题

1. 唤醒后默认发言。运行结束时，最终文本除非是 `[群聊静默]`，都会发布。表情回应（`group_pin`）也作为群发事件通知其他成员。
2. 空闲和忙碌两套判断。空闲 Bot 先经 Laya 选择参与或旁听；忙碌 Bot 在每次模型调用前读入排队的新消息（每次最多 8 条），不判断是否相关。
3. Laya 的题太难，输入还可能被截断（4.3）。
4. 忙碌时不能顺带回一句：消息要么读入当前运行，要么等运行结束。
5. 同时开口没有补救。空闲 Bot 对同一批消息同时开始，互相不知道对方在答，内容重复；被 @ 的还没答，别的 Bot 可能先答了。
6. 谁来做靠群任务。认领要 key 和来源消息，更新要修订号，还有一组续跑和停滞检查推着模型更新。@ 不决定谁做，其他 Bot 也能认领 @ 给别人的事。
7. 上下文混杂：
   - 群提示词中的“原始任务”是本轮的根请求。用户发“@A 做导出”，B 被唤醒时看到的原始任务也是这句。
   - 每次运行附带本群最近 4 轮的用户请求，不区分对象。
   - 其他 Bot 的发言以 user 角色进入上下文，与用户指令相同。
8. 等待占着运行。后台任务没结束，运行不能结束；`process_wait` 每次最多等 30 秒，只能反复调用模型。私聊抢占群聊运行时，这次运行记为取消，它启动的后台任务会被停掉（读代码得出，未复现）。
9. 没有群简介或公告，群的用途和约定只能靠聊天记录。
10. 限流没有生效：Bot 之间的发言有计数，没有限制。

## 四、谁回应

### 4.1 规则

按顺序匹配，命中即停止：

| 顺序 | 条件 | 结果 |
| --- | --- | --- |
| 1 | 本人的消息；表情回应；系统通知（成员变化、置顶） | 不叫醒。表情回应算作对那条消息的答复 |
| 2 | @了本人、回复本人的消息，或系统发给本人的提示 | 叫醒，不问 Laya。用户发的、Bot @了本人的、系统发给本人的，必须回 |
| 3 | @了其他 Bot，或回复其他 Bot 的消息 | 等那个 Bot 先答（含表情回应）或 20 秒后，按第 4 条 |
| 4 | 其余：没点名的、@用户的 | 问 Laya：回应就叫醒，不回应就不叫醒 |

- 消息仍然投递给所有成员，规则只决定叫不叫醒。不叫醒的记为已读，不进入上下文。
- 叫醒后，主模型还可以决定不说（7.1）。
- 回复本人的消息到达时，如果同一条消息下还有人正在输入，等他们发完（最多 20 秒）再一起交给本人。这样征求意见的一方能一次看到所有回复。
- 用户没点名的消息，如果没有 Bot 回应，群里提示“没有 Bot 回应，可以 @ 一个”。
- 第 2 条对应 Telegram 隐私模式下 Bot 一定能收到的消息；第 4 条相当于关掉隐私模式，Bot 看得到所有消息，由 Laya 决定回不回。

### 4.2 @ 的含义

- 被 @ 的必须回，最轻可以是表情回应或“稍后答复”。
- 用户 @ 了哪些 Bot，就由这些 Bot 做（第八节）。其他 Bot 可以回答、补充、指出风险、提出反对，不接手。
- 其他 Bot 等被 @ 的先答，看到答复后只补充没说到的。@用户时不等，其他 Bot 的意见可以帮助用户决定。
- 认为自己更合适，或想分担一部分，可以提出来，由用户决定。
- 不设 @所有人。想让所有 Bot 都回，就把它们都 @ 上。

### 4.3 Laya

- 用于第 4 条，空闲和忙碌都用。
- 只问一道选择题：“当前 Bot 要不要回应这条消息？”
  - 回应：消息和它的职责或手上的事有关。
  - 不回应：无关。
- 输入依次是：职责一句、手上的事一行（成员状态，10.1）、这条消息（前 600 字）、它回复的那条（前 300 字）；按第 3 条等过的，再加被 @ 的 Bot 的答复（前 300 字）。短而关键的放在前面，因为输入超长时截掉的是末尾。
- 去掉现在指令里关于授权和静默的说明，这些由规则和主模型处理。
- Laya 不可用时，按回应处理。
- 误判的后果：误判为回应，主模型看了不说，多一次调用；误判为不回应，消息已记为已读，发送方需要确定答复时用 @。

这样问的原因：

- 模型卡写明，它零样本做定制决策接近随机（0.342，随机基线 0.318，多数类基线 0.461），出厂未校准。
- 问“有没有关系”比问“该不该说”简单：前者只看这条消息和本人职责、手上的事的语义；后者还要考虑别人说没说、说了多少，交给主模型。
- 现在的输入可能被截断。sidecar 没有指定长度上限，本地 `laya_mlx` 包在输入超长时保留开头、截掉末尾。当前输入依次是人设摘要、新消息、前文、`myTask`、`rootRequest`，最先被截掉的是后两项。实际长度还没统计，可以用 `laya-decisions.jsonl` 计算。

改进：Bot 被叫醒后没有发言，记为可能误判；定期抽查不回应的消息。统计出误判率后先校准，再针对群聊微调。数据只在本地使用。

## 五、怎么回应

### 5.1 空闲：启动运行

叫醒空闲的 Bot 时，照现在的方式启动运行。能不能动手看第八节。

### 5.2 忙碌：顺带答复

叫醒忙碌的 Bot 时，做一次顺带答复，不等当前工具结束。参考 Claude Code 的 /btw。

| 项目 | 说明 |
| --- | --- |
| 看得到 | 这个 Bot 在这个群的工作记录（到最近一次保存为止，含已完成的工具结果）、这条消息和它回复的消息、成员状态、群简介和置顶。当前运行在别的群或私聊时，只用这个群的工作记录 |
| 工具 | 没有 |
| 结果 | 四选一：答复（公开发言，可以只是表情回应）；并入当前运行（要在手上的事里处理的，比如用户的修正、对当前方案的意见）；稍后处理（要动手或查资料，但和手上的事无关）；不答 |
| 必须回的消息 | 不能选不答；选并入或稍后时，先回一个表情或一句 |
| 写入 | 问答都不写回工作记录。答复是公开的群消息，以后有人回复它时会随引用带上 |
| 合并 | 同一个 Bot 同时只有一个顺带答复在进行，期间来的消息合并到下一次 |
| 成本 | 一次模型调用。上下文和工作记录相同，模型服务支持前缀缓存时主要是缓存读取 |

顺带答复不是新的运行，不改变“一个 Bot 同一时间只有一个运行”，也不会和当前运行争用桌面、文件或命令。

### 5.3 并入当前运行、稍后处理

- 并入当前运行：在下一个安全点读入，也就是现在读入新消息的位置。改动是只读入顺带答复选了并入的消息，不再把排队的消息全部读入。读入时标明发送者和身份，注明需要回应。
- 稍后处理：消息留在收件里，当前运行不读；运行结束后，照现在的方式作为新一批收件启动运行。
- Bot 在等后台任务时，有要并入的消息会让等待提前结束（第九节）。

## 六、同时开口

### 6.1 取舍

| | 依次开口 | 同时开口（采用） |
| --- | --- | --- |
| 速度 | 后面的要等前面的说完。一个 Bot 答一次通常要十几秒到半分钟，3 个依次答，最后一个要等一分钟左右 | 大家同时开始，和真人群里一样 |
| 重复 | 最少，后说的能看到先说的 | 可能重复，靠发前再看一眼补救；几乎同时写完的两条仍可能重复 |
| 调用次数 | 差不多。Laya 判断的是有没有关系，后说的照样会被叫醒，由主模型决定不说 | 差不多；发前再看一眼偶尔多一次 |
| 抢答 | 不会 | 被 @ 的还没答，别人可能先答；由 4.1 第 3 条的等待解决 |
| 实现 | 要排队、超时、忙闲混排；一个卡住，后面都要等 | 现在就是同时开始，只需加补救 |

几乎同时写完导致的重复，真人群里也会发生，可以接受。

### 6.2 发前再看一眼

从开始生成到发布之间，如果同一条消息下出现了新回复，或者用户发了新消息，先交给主模型确认一次：照发、只补差异、改成表情回应，或不发。没有新消息时直接发布。运行和顺带答复都这样做。复核由发言的 Bot 自己完成，传输层仍不做去重。

### 6.3 正在输入

群里显示“A、B 正在输入”。它也用来判断一条消息的回复是否已经到齐（4.1）。

## 七、发言

### 7.1 不说是正常结果

- 必须回的消息（4.1 第 2 条），运行的最终文本照常发布。
- 其他情况下，要发言得明确调用 `group_send_message`，最终文本不自动发布，不再需要静默标记。
- 顺带答复选不答就不发。

### 7.2 怎么说

- 先给结论，尽量短。同意时用表情回应代替“+1”。
- 同一个论点只说一次，有新信息时再说。
- 需要谁答复就 @ 谁；接着哪条说就回复哪条。想听大家的意见，就直接说“大家看看”。

### 7.3 表情回应

不叫醒任何人，但算作答复。收到但晚点处理时可以用 👀。

### 7.4 有下文

- 被 @ 必回：运行结束前，@了本人的消息还没有答复（发言或表情回应）的，提醒一次。
- 意见有结果：针对自己工作的建议和反对，给出三种结果之一：采纳并说明怎么改，不采纳并说明理由，交给用户决定。运行结束前还没回应的，提醒一次。现在运行结束前对计划没做完、后台任务没核对，也是这样提醒的。
- 征求意见的回复到齐后（4.1），用一句话给出结论，比如“用 B 的办法，因为……”。
- 找用户决定时，写清选项、各方理由和自己的倾向，并 @用户。

## 八、谁来做

### 8.1 动手要有用户交给自己的事

- 用户交给自己的事：@了本人的请求；没点名、本人接手了的请求；本人的计划、目标（/goal）和定时任务。
- 有还没完成的这类事时，这个 Bot 在这个群的运行可以用全部工具；没有时，只能看和发言。现在每次模型调用前都会重新计算工具，接手后立即生效。
- 程序保证的是：没有用户交给的事，就不能动手，被其他 Bot 叫醒也一样。有的时候，只为用户交给的事动手，靠提示词。

### 8.2 接手

- 没点名的用户请求，要做的 Bot 回复这条消息说“我来”，并标为接手。程序把接手记在这条消息上，显示“A 在做”。
- 同时开口时，可能有两个 Bot 同时接手：先到先得。后来的接手不成功，会看到谁接了，可以改成补充，或提出分担，由用户决定。
- 用户 @ 了几个 Bot 时，这几个都算交给了，自己在群里商量分工。

### 8.3 完成

- 运行结束时，交给本人的请求如果没有未完成的计划步骤、没有在跑的后台任务，就自动标为完成，消息上显示“A 完成”。
- 要分几次做的，用计划记下步骤（现有的 `plan_update`）：计划没做完时，这条请求一直显示“在做”，也会被要求继续（现有检查）。跨多次运行的用 /goal。
- 做完时回复这条请求，说明结论和产出位置。
- 用户可以在消息上把请求标为完成，或者取消。
- 被私聊抢占后重新排队的运行，带上上次的计划。
- 删掉群任务后，续跑和停滞检查改为针对计划。
- 同一个群的本机工作目录是共用的。改别人正在改的文件前，先 @对方。

## 九、等待

默认照 pi，同步等。Bot 在等的时候仍在运行：群里的消息由顺带答复处理；用户交代的新事可以并入当前运行（先做，再回来看结果），也可以稍后处理。

改三处：

1. 放宽 `process_wait` 的等待上限：现在每次最多 30 秒，改为最多 5 分钟。10 分钟的构建，模型调用从约 20 次降到 2–3 次。
2. 有要并入的消息时提前返回：等待中，顺带答复选了并入，等待立即结束，在下一个安全点读入。
3. 私聊抢占时保留后台任务：交给重新排队的运行继续核对。显式停止仍然停掉。

以后照 Claude Code 做后台结束通知，条件是几十分钟以上的长任务变得常见：运行可以带着后台任务先结束，任务结束时往这个 Bot 的收件投一条只给它的事件，写明任务、退出码和日志位置。要改运行的结束条件，并防止模型在通知到达前就声称完成，Claude Code 有模型伪造结束通知的问题报告。

## 十、看得见彼此

### 10.1 成员状态

每个 Bot 一行，由程序生成，不调用模型。例：`B · 在做：导出页面（计划 3/5）· 等：构建`

- 在做：交给它、还没完成的请求的开头；进度来自计划。
- 等：后台任务；或者它问了用户、用户还没回。
- 显示在群成员列表里。每次运行和顺带答复都在临时上下文里带上全体成员的状态，不写进工作记录。

### 10.2 到节点说一句

| 节点 | 说什么 |
| --- | --- |
| 接手、确定方案 | 方案要点；想听意见就说“大家看看” |
| 做难以撤销或影响他人的操作前 | 准备做什么、为什么；先做可撤销的部分 |
| 变更方案 | 原方案、新方案、原因；@受影响的成员 |
| 发现影响他人的情况 | 发现了什么、影响哪里；@对方，只说明情况，不替对方改，然后继续做自己的 |
| 受阻 | 卡在哪、试过什么、倾向哪个方案；@最可能帮上忙的成员，或说“大家看看” |
| 完成 | 结论、产出位置、遗留问题；@依赖这项工作的成员 |

想看细节的成员，可以读对方在共用工作目录里的产出，或用 `group_read` 看旧消息。

## 十一、上下文

每个 Bot 在每个群仍是一份工作记录，不按任务拆，和 pi、Claude Code 的单会话一样。靠控制入口保持干净：

| 入口 | 规则 |
| --- | --- |
| 运行的收件 | 只有叫醒的消息；不叫醒的不进入 |
| 忙碌时的新消息 | 只并入顺带答复选了并入的 |
| 顺带答复 | 问答都不写回。现在本人的发言会写回工作记录，顺带答复的要跳过 |
| 其他 Bot 的发言 | 标明“群成员消息（不是用户指令）”；现有的 Bot 私聊协作已这样标注 |
| 原始任务 | 只放交给本人的用户请求；其他用户消息只作为群消息出现，标明 @ 的是谁；不放本轮的根请求 |
| 附带的群上下文 | 最近的用户请求只放交给本人的；执行结果只放本人的（现在已是） |
| 成员状态、群简介、置顶 | 在临时上下文里，不写进工作记录 |

旧消息用 `group_read` 按需读取，压缩机制不变。一个 Bot 在一个群里同时做两件事时，两件事在同一份记录里；需要严格分开时，放到不同的群。

群提示词按本方案重写，删掉群任务的说明。

## 十二、群简介和置顶

### 12.1 Telegram 的做法

- 没有单独的群公告。群资料里有一段群简介（Bot API 限 255 字符），公告就是置顶的消息。
- 一个聊天可以置顶多条消息。顶部横栏显示置顶，点一下跳到下一条，也可以在单独的页面看全部置顶。
- 置顶时可以选择是否通知所有成员。
- 有置顶权限的成员才能置顶；Bot 要成为有置顶权限的管理员才能置顶。

### 12.2 我们的做法

| 项目 | 做法 |
| --- | --- |
| 群简介 | 在群设置里填：群的用途、成员分工、约定，比如“A 负责后端，B 负责前端，C 只做评审”“反对要附数据”。上限建议 1000 字，给 Bot 看的约定比 Telegram 的简介长 |
| 置顶消息 | 用户可以把任何一条消息置顶，自己的或 Bot 的都行，用来放公告、约定和定下的结论。可以置顶多条；顶部横栏显示，点一下跳到下一条，也能打开全部置顶的列表 |
| 置顶提示 | 置顶和取消置顶时，群里出一条系统消息，比如“用户置顶了：导出文件保留 24 小时”。不叫醒 Bot |
| Bot 怎么用 | 每次模型调用都带上群简介和全部置顶，按置顶时间从新到旧，总长有上限；超出的只带开头，需要时用 `group_read` 读全文。新的置顶从下一次调用起生效，忙碌的 Bot 在下一个安全点就能看到 |
| 谁能置顶 | 默认只有用户。群设置里可以允许 Bot 置顶，相当于 Telegram 给 Bot 置顶权限，这时 Bot 可以把讨论出的结论置顶 |
| 和内置规则的关系 | 被 @ 必回、意见要有结果、授权只来自用户、限流这些由程序和群提示词保证，群简介和置顶关不掉。群简介和置顶只交给主模型，不改变程序行为；Laya 不读 |

命名：现在的 `group_pin`、`chat_pin` 是表情回应，消息上的 `pins` 字段也是表情。做置顶前要改名，比如改成 `group_react`，避免和置顶混淆。

## 十三、限流

Telegram 开放 Bot 之间对话时，要求开发者防循环，建议去重、限速、按每对 Bot 和全局限制往来深度或时长。我们做其中的去重和两级深度限制：

- 去重：发件箱已有的幂等保护，加上发前再看一眼（6.2）。
- 每对 Bot：用户最后一次发言后，两个 Bot 之间来回 2 轮，彼此的消息就不再叫醒对方。系统提示讨论所涉工作的负责人汇总双方理由，自己决定或 @用户。负责人指这件事交给了谁（8.1）；分不清时，由先发言的一方汇总。
- 全群（2026-10-06 修正）：用户最后一次文字发言或明确点击继续后，Bot 发布的文字累计最多 20 条。第 20 条落盘后暂停讨论，取消本群待处理判断与运行任务；统一发布入口拦截并发返回的第 21 条，不仅限制后续叫醒。
- 计入的发言：所有 Bot 的普通文字和进度消息，无论是否点名、回复其他 Bot 或答复用户。表情与系统通知不计入；用户表情不重置额度。达到上限后，用户发新消息或点击“继续本轮讨论”重新获得额度。
- 限流优先于“被 @ 必回”，但不限制用户的 @。
- 当前全群上限按用户要求改为 `GROUP_LIMITS.botStreak = 20`，尚无群设置调节入口。整条结束标记（如 `<|eos|>`）与“（空消息，无需回应）”按静默处理，不发布、不叫醒其他 Bot，也不占额度；旧记录在界面中隐藏。正常解释中引用这些文字仍可显示。

## 2026-10-07 群聊边界检查记录

通过反例复现并修复三处问题：同一 Bot 先发布进度、再发布文字相同的正式回答时，发件去重会将正式回答误认成进度；同一次执行分别回复两个问题、文字相同时，第二个回复对象会丢失；旧的空消息已经在页面隐藏，群列表仍将其计入未读。现在发件比较和自动发件标识均包含消息类型及回复对象，重复发送同一回答仍保持幂等；未读统计采用与页面一致的空消息排除条件，带附件的消息继续保留。

新增四项回归覆盖模型最终回答与显式发送两种路径、分别回复两个问题，以及历史空消息未读数。群聊、窗口弹出与私聊隔离共 88 项测试、附件相关 18 项测试、前后端类型检查、相关静态检查和构建通过。既有 20 条发言上限、并发最后回复、停止与恢复、表情不相互唤醒等回归均通过。没有请求真实模型或修改正式群聊数据；这些测试不能证明所有交互路径或真实模型长期讨论均无问题。运行中的 Electron 进程需重启后加载后端修复。

### 同日严格复查与修复收尾

进一步通过故障注入复现多问题回执错误：正常结束、达到发言上限和重启恢复都可能把一个执行中的所有送达记录指向同一回答。现在三处共用 `acknowledgeReplies`：优先匹配同一次执行中明确回复该问题的消息或有效表情，未单独回答的记录才采用最终回复；进度不充当明确回答。恢复时按实际群消息序号选择最新已公开的回执，避免早先创建、稍后重试的发件记录打乱顺序。

同时验证旧格式自动发件标识：曾经写入失败、尚未公开的旧发件记录，升级后重试原先会留下一个永久 pending 记录；现在按消息内容、类型和回复对象复用同一次执行的已有记录，不清除或改写历史数据。显式发件标识若被用于不同类型或不同回复对象，仍明确拒绝。

补充回归包括多问题逐条回执、重启补回执、发言上限时回执、旧待发送记录复用、重试后的真实发布顺序，以及停止后迟到的模型回复不能进入继续后的讨论。所有测试使用隔离临时目录，不请求真实模型。改动限定在群聊服务、两份群聊测试和本记录；没有调整人格策略、模型配置或私聊逻辑。本地观察到仍有进行中的狼人杀对局，未强制重启应用。

最终验证：112 项相关测试全部通过，前后端类型检查、相关静态检查、格式检查、差异空白检查和构建通过。代码与构建产物已更新，当前运行进程尚未重启；没有提交或推送，也没有完成真实模型端到端验收。

### 从测试角度审查逻辑完备性（2026-10-07）

结论：此前按单条成功路径和已知反例测试，不足以宣称逻辑完备。本轮先列状态与不变量，再补组合测试。表中的“通过”只指列出的具体场景，不代表任意事件交错均已穷举。

| 不变量 / 状态边界 | 本轮及已有回归的具体覆盖 | 验证边界 |
| --- | --- | --- |
| 公开文字和进度在用户下一条文字或明确继续前最多 20 条；表情不重置或消耗这个额度 | 直接工具循环、多个 Bot 并发最后回复、继续后重新计数、表情不增加 `round.botMessages` | 后端规则通过；未做 8 个真实模型的长期压力测试 |
| 已确认公开的发送可在进程退出后读取，重试不重复发；失败不能留下半条公开消息 | JSON、SQLite 同步、桌面延迟写盘各注入第 1/2 次提交失败，共 6 个故障窗口；检查正文、投递和上下文回滚；精确重试；旧发件标识兼容 | 提交异常为故障注入，不是真实磁盘满、文件损坏或断电 |
| 文字与表情发送返回成功后不能仅停留在内存 | 按桌面 `incremental + deferWrites` 配置立即重开数据库；两个子进程分别在文字 / 表情成功返回后立即 SIGKILL，检查实际磁盘记录 | 真正强杀的对象仅为隔离测试子进程，不是用户的 Electron 进程；不请求真实模型 |
| 恢复只继续未完成工作，不重做已完成的回答、表情或静默结束 | 3 种存储 × 正常退出 / 模拟崩溃状态 × 文字 / 表情 / 静默完成 / 只有进度的未完成执行，共 24 个恢复组合；多问题回执、乱序重试后的实际消息序号 | 任意历史版本损坏数据和多次连续异常退出尚未穷举 |
| 重试应恢复整个失败执行，并保留已处理输入；结算后的输入不能被重新打开 | 2 个输入的失败批次全部恢复；14 个输入只恢复一次原执行；已回复、已忽略和达到上限的送达记录拒绝重开 | 超大批次的上下文容量和性能尚未压测；没有改上下文限额 |
| 停止、成员移除或删群后，旧执行的迟到结果不能发布 | 停止再继续时迟到文字被丢弃；移出后重加、删群时迟到工具调用不进入发件箱；停止撤销待授权写文件 | 没有在真实模型网络请求中执行这些操作；使用可控的延迟模型夹具 |
| 进度不等于回答；调度、回执与界面未回答判断采用同一含义 | 指向问题的进度不能释放“已有回答”判断，静默结束只提醒一次然后标记忽略；正式回答可重复进度正文；多个问题相同正文各自保留回复对象 | 回答内容是否真的解决问题，仍属于模型质量 / 人工评测，不由状态测试判断 |
| 表情是已送达的回应，不触发 Bot 之间接龙 | Bot 表情广播但不唤醒其他 Bot；有效表情可完成回应；写入失败回滚徽标、事件、投递和新轮次；重试只创建一次 | 用户表情仍可唤醒消息作者，沿用既有产品规则 |
| 群、私聊、成员权限与附件边界保持隔离 | 私聊上下文回归、移除成员后拒绝读写、同名 Bot 的真实 ID、附件可见性和转发、工作记录不进入私聊 | 未覆盖所有外部工具权限组合 |
| 游戏窗口打开时不强行弹出 Bot 预览 | 原生 dialog / 嵌套覆盖层的阻塞与释放回归 | 本轮没有完整重跑真实 Electron 的游戏＋群聊＋预览点击流程 |
