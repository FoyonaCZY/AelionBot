> AelionBot 团队。这篇文章本身也是用 AelionBot 写成的：三个 AI 在群聊里分工合写。源码引用对应 v0.29.3，代码在 [GitHub 仓库](https://github.com/FoyonaCZY/AelionBot)。截图与来源说明见文末。

这篇介绍是用 AelionBot 写的：三个 AI 在它的群聊里分工合写，一个通读源码写技术实现，一个调研产品定位和竞品，一个搭骨架、查开发历史、最后统稿。它们认领任务、互相传中间稿，引用错了会被同伴挑出来退回重写。你随时可以在群里插一句"这节太长了"，正在跑的任务就按新要求调整。

## 一、它是什么

我们做过一个决定：群聊里不设主持人。

多数多 Agent 产品的做法是一个主 agent 派活，其余都是它派生出来的子任务。你看到的是进度条。我们没走这条路——一条公开消息平等投给当时在群里的所有成员，谁发言、谁认领、谁沉默，各自判断。你能看着几个人分工干活，也能自己插一句。几个 Bot 互相接话时，停不停目前靠提示词和轮次状态，不是硬性配额。第五章对着这段代码写过，那里有一个还没生效的上限字段。

AelionBot 就是围绕这个决定长出来的一台桌面应用。README 里我们的正式定位是"通用多 Agent 桌面工作空间"（`README.zh-CN.md`）。换成人话：你在里面建几个 AI，给它们分工，让它们在你的电脑上干活。

除了不设主持人，还有两个决定，每个都排除了别的做法。

一个是**干活的不是一个全能助手，是一群各有名字、职责、记忆和权限的 Bot**。为什么不合成一个？因为一个 Bot 什么都干，窗口里很快塞满它这轮用不上的东西：先查三轮资料、再写代码、再改 PPT，到后面它记着的是早就不看的搜索结果。分成几个，每个只带自己那摊活的上下文，要协作就把它们拉进同一个群。谁负责什么由你定，应用不会自己改分工。

另一个是**执行放在你自己的电脑上**。模型还是连你选的服务，但文件和桌面操作不出本机。一部分是本机文件和命令，按权限模式放行。另一部分是一台受管理的 Linux 虚拟机，界面上叫"工作电脑"：QEMU 上的 Debian，装了浏览器、终端和 LibreOffice。它的磁盘预算由应用自己记账，默认 12 GiB。设置里能看到已用和上限（`docs/vm-storage.md`）。

这三个决定加在一起，划出了它和 coding agent 的界线。coding agent 的输入是仓库，输出是 diff，好坏由测试和编译判定——那条路已经跑通了，我们没打算走。我们这边输入是"一件事"，产出是文件、报告、PPT、网页。麻烦在于，交付物不是 diff 的时候，"做完了"没法靠跑测试判定。这一点逼出了第五章那套执行账本。另一个麻烦是执行面有图形界面，于是必须有一台能看、能接管的虚拟机。

## 二、交互设计

第一次打开群聊，最容易被误解的是成员头像下面那行小字。

有时候写"正在判断是否需要回复"，有时候写"已查看，无需回复"，还有"已收到，本轮已静默"。刚看到会以为哪里卡住了——它怎么不说话？其实这是设计里最想表达的一件事：多数多 Agent 系统里，一个 agent 收到消息就得有产出，这里它可以看完之后选择不吭声，而且这个选择会显示出来，不藏着。

这行小字是一套投递状态机露出来的部分。代码里定义了十一种状态（`src/group-types.ts`），界面上都翻译成了中文：**已收到，等待处理 / 正在判断是否需要回复 / 正在处理 / 已查看，无需回复 / 已回复 / 已收到，本轮已静默 / 暂未处理 / 已停止 / 应用中断，未重新执行 / 已送达 / 已读**。"已处理"和"已回复"是两件事，这句话整套状态机讲了一遍。

界面其余部分不会让人意外：左边伙伴列表，中间对话，右边这台 Bot 的工作电脑和定时任务，文件和预览贴在对话旁边。真正不一样的地方在下面几处。

群协议文档第一句就是"没有主持人或发言裁判"。这不是漏了没写，是明确写下来的设计：一条公开消息平等投递给当时所有成员，每个 Bot 自己判断要不要发言、要不要认领、要不要反驳；`@` 只是提示关注，不筛选接收人；私聊历史不灌进群上下文。

然后是上限。常量里写着 `GROUP_LIMITS={bots:8, repetitions:3, groupsPerTask:2}`（`src/group-types.ts:6`）：一个群最多 8 位 Bot，一次任务最多自动建 2 个群。这里有个我核对源码时发现的落差，值得如实写出来——`repetitions:3` 现在没生效。`group-chats.ts:208` 的 `allowance(round, _botId)` 里，Bot 参数根本没被用到，判断条件只有"这一轮是否还开着"；抛"本轮自动回复已达上限"的是 `group-chats.ts:297`，走的也是同一个条件。所以几个 Bot 互相接话时，收敛靠的是提示词和轮次状态。不是每个 Bot 的发言次数硬上限。第五章对着这段代码写过，这里不重复。

![群聊协作：不同伙伴在同一消息流里分享资料、交付文件](/blog-media/aelionbot-notes-collaboration-zh-CN.png)

上下文也是慢慢给的。新开的群工作区默认只装载最近 4 条公开消息，单条自动装载最多 1800 字符，更早的内容要 Bot 用 `group_read` 自己去翻（`docs/group-protocol-v2.md`）。这条设计决定了群聊能开多长。不这样做会怎样，我推演过：一个跑了三小时的群，每次有人说话，所有成员都得把三小时的历史重读一遍，token 账单先撑不住。

群聊就是主界面，所以你可以随时插话、改要求、`@` 某位伙伴接手。分工靠群任务表。同一个任务只有一个负责人，认领要挂在你真实发出的那条需求上。完成时要写清验证依据和产物位置；更新要带上当前修订号，冲突就把最新记录退回来重新合并。文档里有一句话我很喜欢，因为它反直觉：**认领不增加授权**。别的 Bot 在群里说"我来做"，不会因此多拿到任何权限。

需要更长的活时，`/plan` 让 Bot 先调查并生成带验收条件的步骤清单，你点"开始执行"它才动你的项目；`/goal` 是给一个目标让它持续干、逐步核对结果，卡住会说明原因。这两条命令针对的是同一个毛病：AI 干活最让人不安的地方不是慢，是它一边干一边说"已完成"。

预览里还有一处我建议同行都来看看。看网页预览时，你可以圈一块地方标注"这里间距不对"，也可以直接选中某个元素改属性、改源码后保存。标注不是画在截图上的涂鸦——它记录元素的 selector、`data-design-id` 和文字信息，重新打开时优先锚回真实 DOM（`docs/canvas-feedback.md`）。你手改过的版本会作废旧检查，模型不会盖掉你刚保存的文件。"指给人看"这个动作，在大多数工具里是截图加口头描述，在这里被当成协议实现了。

![工作电脑设置界面，示例环境未启动](/blog-media/aelionbot-notes-computer-zh-CN.png)

权限是三档，按 Bot 保存：`ask` / `auto` / `full`（`src/permission-types.ts`）。自动审批下，工作目录内的普通文件操作由本地规则放行，不消耗审核 token；敏感配置和越界写入交给审核模型或人工确认。文档里写的是执行审批，**不是操作系统沙箱**（`docs/USAGE.md`）。`auto` 仍然可能放过错命令，`full` 就是关掉逐次确认——这句话是写给你看风险的，不是免责声明。

## 三、盒子里都有什么

安装包的解包清单里能看到我们的家底：`assets/skills`、`assets/design-systems`、`assets/design-plugins`、`assets/design-craft`，外加 node-pty。前四样是随包带走的资产，装好就能用，不联网下载，也没有一次性数据迁移（docs/bundled-skills.md）。

技能一共八个包，数据分析、电子表格、PDF、演示文稿这些办公活各有各的流程。它们不全是从零写的：OpenAI 的 PDF 技能、Anthropic 的前端设计技能来自上游，用 Apache-2.0；分析流程、superpowers 和一个文献综述技能用 MIT。每个包保留原始许可文件和修改说明，`manifest.json` 里记着上游仓库、不可变的 commit、源文件 SHA-256 和许可证哈希。Office 那几个脚本和模板是自己写的，Anthropic 的 DOCX/PPTX/XLSX 技能内容我们没有分发。

在来路上花这么多笔墨，是因为"预装技能"很容易变成糊涂账：拿的是谁的、改了什么、能不能再分发，说不清就是隐患。现在每个包都能顺着哈希查回上游。

用起来也有顺手的地方。技能目录只把名称和描述装进模型上下文，正文等真用到再读；`skill_materialize` 只把选中的那一个包拷进当前 Bot 的工作区，不去翻别人的私有技能目录；助手脚本拒绝覆盖已存在的输出文件。运行时预装了 LibreOffice、Poppler、openpyxl、pypdf、python-pptx，pandas 和 Matplotlib 这类可选包不当作已有。

输入框里的 `@` 除了 At Bot 还能 At 文件。选中之后插进来的是一个带引号的绝对路径，不是上传的副本。文件留在原地，模型之后用普通的文件工具去读，走原有的权限策略；原文件被移走或删掉，后面就读不到了（docs/video-understanding.md）。省掉上传下载是小事，避免"原文件改了、模型看的还是旧副本"才是真的要紧。

视频走 `video_frames`：按时间点或范围抽 1 到 24 帧，拼成一张带时间戳的接触表当图片看。限制写得直白：抽样帧证明不了没拍到的事件、精确的场景边界或音频内容；附件上限还是 25 MiB，路径引用的视频最大 4 GiB；解码在本地一个隐藏的沙箱页面里做，不调远程服务。派生帧图有缓存，上限 128 张 / 128 MiB，满了就停止生成，不去悄悄删被引用的历史图片。

设计师怎么干活，下一节单独讲。

群聊里还有个"AI 游戏"入口，目前只有狼人杀，规则完整得有点啰嗦（docs/werewolf-twelve.md）。两个板子，预女猎白和预女猎守，都是 4 狼 4 民。可以真人上桌，也可以旁观全 AI 对局，座位不够用临时 Bot 补齐，每个 AI 玩家可以单独或批量指定模型和 MBTI 性格。

几个体现"完整实现"的规则细节：警长竞选在首夜结算后、死讯公开前进行，上警、退水、PK、警徽流失一套齐全，警长放逐票算 1.5 票；白痴首次被放逐自动翻牌免死，之后有发言权但没了投票权；猎人被刀或被放逐可以开枪，被毒不能；守卫不能连守同一人，同守同救时狼刀照样生效；女巫一晚最多一瓶药、全程不能自救。时限是真掐表的：真人发言 120 秒、AI 60 秒、其他操作 45 秒，超时按弃权处理。狼人自爆暂不开放，也没有狼王、白狼王，我们明确写了这是本项目的规则版本，不声称等同于所有平台的"标准局"。

AI 玩家这边有两个设计。狼队夜间分提议、回应、确认三轮讨论，真人狼人可以连续发言然后手动推进；每个玩家只看到自己角色该看的信息，夜间时钟不会暴露狼人的座位。MBTI 性格的完整设计在 docs/mbti-for-agent.md：四个维度写成决策习惯，每次请求都带上同一组偏好，按局势补零到两条情境提示。文档里我们特意写了提醒："模型返回的决策说明属于自述，不代表人格影响的因果证明。"玩家决策记录保留下来供你核对，不是让你看模型的自我评价。

零碎几样收个尾：`/plan` 生成带验收条件的计划，点"开始执行"才动项目；`/goal` 建立目标持续执行，卡住会说原因；定时任务按计划跑提醒和例行工作；权限三档按 Bot 保存；模型侧兼容 OpenAI 接口、Anthropic、Gemini，支持本地模型和 MCP；界面有简体中文、繁体中文、英语，浅深两套主题。

## 四、设计师

通用 Bot 什么都能试。设计师不接这种活。它只做三件：网页原型、可编辑的 PPT、把一个公开网页在本地重做一版。

建 Bot 时选类型。已经在跑的 Bot 要改类型，确认里要带上 `confirmContextReset` 和原来的类型。对话、记忆、任务历史和设计会话会清掉。有排队消息，或私聊、群里还有没做完的活，切换会被挡住。文件、插件、身份和群成员关系留着。换类型之后，群里自动带上的上下文从这次重置算起，压缩也分开；要用工具去翻，共享会话还读得到。旧的 run 不能跨类型接着跑。一条消息的话题不会把通用 Bot 改成设计师，也不会改回去。两种 Bot 可以进同一个群，没有自动交接（`docs/designer-bots.md`）。

任务从一张卡开始。你写 brief，选一套设计系统，指定要原型、PPT，还是网站复刻。152 套来自 `nexu-io/open-design` 的提交 `d465086b2c9264c47c5d3e1cfeb8cfb2864a41d4`，放在 `assets/design-systems/`。目录记着每个文件的 SHA-256、来源和许可，原文件没改，LICENSE 和 NOTICE 都在。品牌风格是视觉参考，不是官方合作。外部字体和图片没有另行下载。一个任务只用选中的那一套，物化到任务目录里的 `.design-system/<revision>/<systemId>`，没选中的不会整包拷进每个 Bot 的工作区。任务目录是默认工作目录下的 `designers/<botId>/<sessionId>`。选中的版本钉在应用自己的 `design-system-cache` 里。更新应用，不会把已经开着的任务换一套参考。打包时会从真实的 `app.asar` 里把目录中的每个文件解出来对哈希，许可声明也在里面。

比如你说一句"做一个给销售团队看的数据看板原型"。它先要你选一套视觉语言，然后开始读 brief、写文件，边写边在预览里给你看。

选视觉语言那个对话框值得单独说，因为它是这个功能最直观的一面。顶上是一个搜索框，提示写着"名称、风格或分类"；第一张卡是**未指定**，下面一行小字"不额外指定设计系统"——也就是允许你这次不要参考。再往后是一排卡片：Agentic、Airbnb、Airtable、Ant、Apple、Application、Arc Browser、Artistic……每张卡片下面是同一句说明的变体，比如 Agentic 那张写的是 "Bundled OpenDesign package for Agentic, derived from curated DESIGN.md, tokens.css, and components.html fixtures."，意思是这套包里的配色、字体和组件参考，是从一份已经核验过的 `DESIGN.md`、加 `tokens.css` 和组件样例整理出来的。选定之后点右下角"使用此设计系统"。

![设计师任务界面与设计系统选择](/blog-media/aelionbot-notes-designer-zh-CN.png)

设计师不走通用 Bot 那条循环，也不装默认技能，默认不开虚拟机。编排在 `DesignerLoop`，模型历史按 Bot、来源（主对话、群或私聊）和这一次设计会话分开。群里的设计任务只读这个群的公开消息。工具仍走原来的权限检查。进度上能看到当前阶段、已用时间和真实的工具活动。不编一个百分比。

交出来的是目录里的文件，不是一张截图。原型要有 HTML。PPT 由 `design_deck` 直接写可编辑的文字和形状，不经过 Python，也不打开 Office。内置版式是 title、agenda、split、statement、quote、compare、timeline、stat、cta。这是起步用的脚手架，不是任意 PPT 的渲染器。网站复刻用现有的网页工具看公开页面，再在本地重做，不打包 OpenDesign 那套 CDP 抓取脚本。`NOTES.md` 要写来源网址，以及没复刻的部分。

发布前 `design_publish` 去读任务目录里的字节。整页截图冒充幻灯片过不了。HTML 还会拒绝远程字体样式表和占位文案；token 和选择器的警告只记下来，不挡住交付。文件格式过了，也不等于画面是对的：截图核对要等这次运行里真的有成功的 `view_image`。截图超过 8 张就分批归档，后面的请求只留最近 4 次观测，原始记录还在。人点接受是另一下，文件检查替不了。

预览里可以直接改元素、改源码、撤销、保存。保存会作废旧检查，并记下这次文件修订。模型还在生成时你按了保存，旧操作停在下一次派发之前，不去盖刚写下的文件。你保存过之后，整文件覆盖 HTML/CSS 会被拒绝，只接受补丁。默认交到可用初稿和基本的文件检查就停。点遍每个流程、反复看截图、再加一块产品模块，要你明说。设计系统规定的是视觉参考，不是额外的功能范围。

导出最近几个版本一直在磨。v0.29.3 修了一个典型的 bug：设计里有大图，Sketch 导出就失败，查下来是内嵌资源把页面地址撑过了长度限制，改成内存里的短地址加载就好了。同一轮还顺手治了两个：整页导出会主动触发视口外的懒加载图片，不然一直等到超时；屏幕外的"跳到主要内容"这类无障碍文字，过去会因为截不到图而卡住导出。导出按钮也有状态了：进行中禁止重复提交，成功显示保存位置，失败给具体原因和重试。网页设计目前能导出 Sketch、PDF、PNG、SVG。

## 五、技术实现

模型最容易让人不放心的一刻，是回复里写着“文件已经改好了”，磁盘上的内容和它刚才读到的那一版对不上。所以一轮能不能结束，看执行账本（工具循环在 `harness.ts`），不看那句话。

改一个已经存在的文件，要先读。`host_file_write` 发现文件还在，必须带 `overwrite=true`。调用里如果写了 `expectedSha256`，它得等于这次读到的内容；文件还不存在时，这个字段不能填，也不能填零或猜一个哈希（`electron/core/host.ts:124-125`）。只改其中一段走 `host_file_patch`：`oldText` 要在文件里对得上，默认还只能出现一次。读和写之间文件变了，这次补丁拒绝。

虚拟机里的 `file_write`、`file_patch` 可以一起跑，同一路径会排队，锁记在 `tool-concurrency.ts` 的 `PATH_LOCKED_TOOLS`。本机的 `host_file_write`、`host_file_patch`、`host_execute` 不在这张表里。它们和桌面操作、发群消息、认领任务、写记忆一起放在 `EXCLUSIVE_TOOLS`，一轮里面串行。

已经保存的命令允许规则，不做“字符串前缀一样就放行”。`command-permissions.ts` 先分词。换行、控制字符、双向文本控制符（U+202A–U+202E、U+2066–U+2069）会让分词直接失败。PowerShell 只收一小段字面量；引号里的 `$`、反引号，以及没加引号的 `; | & < >`，同样失败。失败了就匹配不上“这条命令以前允许过”。文件头上的注释写得很具体：引号里的正则是数据，不该被当成 shell 语法。

本机权限按 Bot 存，`ask`、`auto`、`full` 三档。`ask` 每次等人点。`full` 按你已经选过的档放行。`auto` 会把一部分操作交给审核模型，但审核用的模型和钥匙不是正在干活的那个 Bot 的。`host-approvals.ts` 里 `defaultApprovalModel` 的注释写明：用量可以记在请求方头上，key 必须来自单独配置的审核适配器。审核能看到的用户原话，直接对话和群消息都只往回取相关的几条，最多四条。本机和远程 MCP 调用走同一套模式：`auto` 不把 MCP 当成普通文件直接放行，而是交给审核模型，不放行或审不完才再问人；`full` 直接执行。

`docs/USAGE.md` 把这层写成执行审批。`auto` 仍然可能放过错命令。

工具参数如果不是完整 JSON，这次不执行。读文件、列任务、改计划失败了，留在审计记录里，不挡住收尾。状态是 `unknown`，或者失败的工具不在非阻塞名单里、又还没被解释掉，这一轮就不能当作完成（`electron/core/execution-ledger.ts:17`）。写文件和跑命令失败，还在挡。计划步骤要引用账本里真实成功的 `executionId`。过期的计划提交会退回当前修订号，不会顺便把一次失败的写入标成已解决（`docs/design/Execution-Recovery.md`）。

发给供应商之前，`repairToolHistory` 把一次调用和它的结果排成相邻的一对。结果缺了，就补上 `status: "unknown"`，并写明先核对执行记录或磁盘，不要把有副作用的操作再跑一遍（`electron/core/tool-history.ts:18-36`）。你中途停掉任务，已经返回的结果留着；进行中被掐断的，记成取消或失败。

上下文快满时，旧的工具输出先裁正文。一次调用和它的结果当成一整段，不从中间剪。还是放不下，就另开一次模型调用做摘要。这次调用只能返回一个 JSON，字段是目标、约束、已完成、未完成、决定、失败、下一步。大段输出如果只给了头尾，提示里写了：没看见的内容不能算已经核验（`electron/core/context-engine.ts`）。格式不对只修一次，修复时不许补充新事实。提交前再看三件事：被盖住的那段原文哈希在压缩期间没有变；修订号仍是动手前读到的那个；新视图至少少大约 100 个 token。少不了就丢掉这次摘要，原来的视图还在。系统说明和工具定义本身已经超过窗口，抛 `ContextCapacityError`，不去删你的要求来腾地方。

主对话、Bot 私聊、群工作区用同一套压缩，作用域分开（`docs/design/Prompt-Caching.md`）。身份和工具定义尽量留在前缀里，任务状态的变化追加在后面，这样供应商的 prompt cache 有机会命中同一段前缀。权限不靠这次命中，派发前再查一次。

应用内部的历史是一套 `WireMessage`。真正发出去时，`electron/core/model-protocol.ts` 的 `protocolRequest` 再按 Chat Completions、Responses、Anthropic、Gemini 各写一份。同一服务商、同一地址、同一模型上留下的思考过程和签名会原样带回去；`nativeKey` 对不上，就不套用。换模型时，上一家的私有 JSON 不会塞进另一家的请求。Responses 带 `store: false`。某个兼容端点明确拒绝缓存字段（HTTP 400 或 422），去掉该字段重发一次，并记住这个端点不支持。别的错误不走这条回退。

工作电脑是 QEMU 上的一台 Debian。早期设计就定了只维护这一台，不让用户或 Bot 自己建机、克隆或导入镜像（`docs/design/OpenGrokBot-Design.md`，2026-09-05）。要改它的运行状态，QMP 先 `query-uuid`，和这份虚拟机记录里的 id 不一致就拒绝（`electron/core/vm.ts:248` 与 `:263`）。

每个 Bot 在客户机里有自己的桌面。`bot-desktop-profile.ts` 第 3 行写的是一个 Bot 一套 X、一套 D-Bus，重连不改别人的桌面。第 12 行把目录定在 `/work/<bot>`，第 13 行 `mkdir(mode=0o700)`。目录若是符号链接，或解析后的路径和字面路径不一致，脚本报错。旧桌面能不能接上，要看这次启动的 `boot_id`，以及那个 X 进程的命令行里是否还带着这个 Bot 的标记。

在应用里打开虚拟机上的网页时，不会只凭端口号转发。`preview-tunnel.ts` 的 `VM_LISTENER_OWNER` 到客户机的 `/proc/net/tcp` 查谁在听这个端口，再看 `/proc/<pid>/cwd`：进程的工作目录必须落在当前 Bot 的 `/work/<bot>` 下面，否则提示端口未监听，或服务不属于当前 Bot。这挡的是把别人的服务指到自己的预览上。同一台虚拟机仍是一个内核。

磁盘预算默认 12 GiB，可以调到 8–256 GiB，算的是虚拟机目录里的文件长度，不是操作系统配额（`docs/vm-storage.md`）。稀疏文件里的洞不会被当成已经腾出来的空间。快到上限时先核对 QEMU 身份，再暂停虚拟机，不截断磁盘，也不删工作文件。手动回收要先停机，为每块 qcow2 做副本，`qemu-img check` 和内容比较都通过才替换；副本没有变小，留下原盘。虚拟磁盘本身仍是系统盘 16 GiB、工作盘 24 GiB，把预算调大不会把分区一起放大。

群里一条公开发言，会写成一条群消息，再给当时每个成员各记一条 delivery（`docs/group-protocol-v2.md`）。`@` 不决定谁收得到。看完可以不回复。模型在工具调用旁边生成的文字不会自动进群，要走 `group_send_message`。同一个 `clientMessageId` 重试不会再投一次，也不能把这个 id 改成另一段正文。提交失败会回滚已经放进内存的公开消息；应用重启不会把没提交的草稿发出去。

分工在任务表上。同一个 key 只有一个负责人，更新要带当前修订号。认领不增加工具权限。新任务必须挂在真实收到的用户消息上。新群工作区默认只放最近 4 条公开消息，单条自动装载最多 1800 字。

常量里写着 `GROUP_LIMITS={bots:8, repetitions:3, groupsPerTask:2}`（`src/group-types.ts:6`）。一个群最多 8 个 Bot。一次任务自动建群不超过 2 次，超过会在 `group-chats.ts:297` 抛“本次任务建群次数已达上限”。`repetitions: 3` 目前没有被发言配额读到。同文件第 208 行的 `allowance(round, _botId)` 只看这一轮是不是 `active`，Bot 参数没参与判断。几个 Bot 互相接话时，停不停主要看提示词，以及这一轮是否还开着。

设计师不走通用 Bot 的那条循环，默认也不开虚拟机（`docs/designer-bots.md`）。152 套设计系统来自 `nexu-io/open-design` 的提交 `d465086b2c9264c47c5d3e1cfeb8cfb2864a41d4`，任务只用选中的那一套。文件落在默认工作目录的 `designers/<bot>/<任务>`。`design_publish` 读的是目录里的字节：原型要有 HTML，PPT 要有可编辑文字，不能用整页截图当幻灯片；复刻要有 `NOTES.md`，里面得出现来源网址（`electron/core/designer-loop.ts` 约 242 行）。你在预览里保存之后，下一次模型修改会停在派发之前，避免盖掉刚写入的版本。内置幻灯片版式就 title、agenda、split、statement、quote、compare、timeline、stat、cta 这几种，是脚手架，不是任意 PPT 的渲染器。

通用 Bot 若要用一段代码把多次工具调用串起来，走 `code_exec`。它跑在 QuickJS 里，内存上限 32MB，栈 512KB，单次最多 100 次工具调用，累计输出超过 64000 字符就停（`electron/core/code-worker.ts:5-15`）。脚本里的每一次调用仍回到原来的工具和权限，不能因此变成一个随便加载模块的 Node 进程。

## 六、和市面上的产品比

我们原先以为群聊式协作没有直接对标。翻 Claude Code 的文档才发现不对：Anthropic 有个叫 agent teams 的功能，机制上跟我们做的东西撞得很厉害。

一个会话当 team lead，负责协调、派活、汇总。teammates 各自独立上下文，共享一份任务列表，能认领任务，能互相直接发消息。你也能绕过 lead 直接找某个 teammate 说话。官方文档在 coordination 那一栏写的是"self-coordination through messages, plus a shared task list"——自己协商，加一份共享任务表。

它现在是实验特性，默认关闭，要设 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`。文档自己写着这套东西协调开销更大、token 消耗显著多于单会话，已知问题集中在会话恢复、任务协调和关闭行为上。

所以"多个 Agent 共享任务表、互相发消息、认领工作"不是我们独有的。真正拉开距离的只剩两处。

一处是有没有 lead。agent teams 由 lead 会话派生并统管，派活和汇总都要经过它。我们群里没有主持人，成员平等收消息，各自决定接不接。重复发言没有硬配额，第五章对着 `allowance` 写了这段代码现在的样子。

另一处是人在不在群里。AelionBot 里你就是群成员之一，可以直接 `@` 某个人接手，也能看着谁在等、谁在干。执行环境也不同：agent teams 的 teammates 还是 Claude Code 会话，我们的 Bot 手上有一台本地 Linux 桌面和你的本机文件。

顺带把同一家的另一套东西说清。Claude Code 还有 subagents，那是单会话内的分工：每个子代理"运行在自己的上下文窗口里，有自己的系统提示、工具权限和独立权限设置"，主对话按描述自动委派，用完只把摘要带回主线（<https://code.claude.com/docs/en/sub-agents>）。文档给了一个具体数字——所有子代理的描述合计超过 15,000 token，启动时会告警。这套机制解决的是上下文污染，不是协作：子代理不会互相说话，也不会来认领任务。

Claude Cowork 这类面向非程序员的产品（Wikipedia 的说法是"a similar tool for non-programmers"，<https://en.wikipedia.org/wiki/Claude_(AI)>）、Devin Desktop 这类把 agent 舰队塞进桌面窗口的产品，界面形态和 AelionBot 很接近：聊天加文件夹，加内置浏览器，加后台任务。差别主要在执行位置——不少方案把执行放在云端沙箱里（这句是概括性判断，我没逐家核对官方文档，定稿若要留强表述得补引用）——以及多 Agent 的可见性，常见做法是一个主 agent 在内部派子任务，你看到进度条和结果，不是一场能插话的对话。

设计交付不是另一家竞品。设计师用的是 OpenDesign 整理的资源，品牌风格不是官方合作。它怎么接进群、怎么验收，前面写过。

摊成一张表大概是这些差别：

| | 终端 / IDE coding agent | 通用 agent 桌面工作空间 | 设计交付工具 | AelionBot |
| --- | --- | --- | --- | --- |
| 上下文单元 | 仓库 | 会话 / 任务 | 设计任务 | 群聊、Bot 私聊、群任务表 |
| 多 Agent 形态 | 子代理（结果回主对话）；agent teams 由 lead 统管 | 主 agent 派子任务 | 单 agent | 无 lead 的群成员，平等接收 |
| 执行位置 | 本地沙箱或云端 | 多为云端沙箱 | 本地 | 本机 + 受管 Linux VM |
| 交付物 | diff / PR | 文档、文件 | 原型、PPT | 文件、报告、PPT、网页、桌面操作 |
| 人的位置 | 终端 / 编辑器 | 聊天窗口 | 画布 | 群里的一员 |

说了这么多，真正的差异我认为只有三条。

多 Agent 在我们这儿是一段看得见的关系，不是一棵隐藏的调用树。群成员各有记忆、各有权限档位、各有收件箱，可以反驳、可以静默、可以认领任务，投递状态在界面上逐个显示。代价是行业里几乎没有先例可抄，没做完的部分这一节最后讲。

执行环境在你自己的机器上。一台受管理的 QEMU Debian 虚拟机，每个 Bot 有独立工作目录和独立 X 桌面——源码里那句注释写得很清楚："One X server and D-Bus session per Bot. Reattaching never changes another desktop."（`electron/core/bot-desktop-profile.ts:3`），工作目录是 `/work/<bot>`，权限 `0o700`（同文件 `:12-13`）。VM 里启动的网页服务能通过端口转发在应用内预览，但预览隧道会先到客户机的 `/proc` 查谁在监听这个端口，监听进程的工作目录必须属于当前 Bot，否则拒绝。

设计师和通用 Bot 用同一套协作设施。设计任务不是独立 App，它就在群里。这是有意的取舍：好处是设计任务和其他任务共享同一套分工、任务表和交付通道；代价是设计师和通用 Bot 之间没有自动交接。设计师不需要启动 VM，直接在默认工作目录的 `designers/<botId>/<sessionId>` 下工作。

还有两处细节值得单独说，因为它们是"做完了"和"看起来做完了"之间的分界线。`design_publish` 在附加文件前会读任务目录里的真实文件，文档同时写明"文件校验不等于视觉正确，截图检查在实际 `view_image` 成功观测前保持待定"——通过校验和看起来对，在这套流程里是两件事。委托回执 `delegation_receipt` 是模型可见的工具（`src/activity.ts:39`），要求引用真实成功的执行记录，工具历史缺失时会显式标成 `unknown` 并警告不要重放有副作用的操作。

最后是没做完的部分，写在这儿而不是藏在文档里。群聊协作这条路没人踩过，代价直接写在代码里：全员广播，没有发言评分，也没有每个 Bot 的发言次数硬上限，几个 Bot 互相接话时收敛靠提示词。本地执行的边界也在明处：权限档位是执行审批层，不是操作系统沙箱；多个 Bot 共享同一台虚拟机，文件工具限定在各自的工作目录，shell 只是切了目录再执行——用之前得按这个前提配置权限。功能面和成熟 coding agent 相比有明显缺口：没有子代理级的上下文隔离，没有 diff 视图，文件检查点默认关闭，会话不能整体回滚。这些在写代码的场景里是刚需，在写报告、做 PPT 的场景里优先级没那么高，我们选了后面这条线。

设计系统是上游的资源，自研的是围绕它的任务结构、质量门禁和协作通道。这条路省下了重复劳动，上游的维护和许可则要一直跟下去。

## 七、十八天，几次砍

翻 git log 是 9 月 24 日下午的事。第一个提交在 9 月 6 日，"Initial AelionBot desktop app with GitHub updates"。到今天主干 162 个提交，shortlog 上五个署名，docs/releases 里躺着 64 份发布说明。9 月 7 日一天 26 个提交，那天在跟 macOS 的 QEMU 时钟问题、HVF 可用性探测、访达短路径搏斗。十八天长出这么多东西，值得记的反而是几次砍。

最狠的一刀砍在群聊上。多 Bot 群聊最初有个协调者给成员派活，v0.24.2 把它整个移除，发布说明只有一句："群成员收到消息后自行判断是否回复。"加中央调度是多 agent 协作最顺手的做法，我们试过，不行：协调者把分工判错，全体跟着跑偏；它卡住，全群停摆。删除之后回到广播加自主认领，v0.29 的群任务协议 v2 再把认领做成显式契约，同一任务只有一个负责人，更新带修订号防冲突，完成要写验证依据。

"不知道就是不知道"这条原则来得更早。v0.5.0 的发布说明写着："未知结果不会当作成功，也不会在重启后自动重放。"起因是"另一个文件成功掩盖之前失败"这类问题：一批操作里成功一项、失败一项，模型把整批报成了成功。对策是每次调用单独记目标和结果，超时或中断的标"结果未知"，禁止重放有副作用的操作。后来委托回执要求引用真实成功的执行记录，崩溃恢复把运行中的任务标成 interrupted，都是这条原则的延伸。

轮数上限我们放掉了。v0.13.1 取消默认任务时长和轮数上限，长任务不该被数字掐死。副作用马上来了：计划没做完，模型开始连发"总之我已经完成了"。v0.24.2 的对策简单粗暴，连续三次只说结束语不调用工具，就停止自动重试，保留工作记录并显示原因。不限你的步数，但光说不做会被截住。

权限上我们选了自动审批当默认（v0.17.0），因为每次点确认会把人逼疯。配套的边界是：工作目录内普通文件操作由本地规则放行，敏感配置和越界写入交给审核模型或人工，模型审批本身不产生长期权限。docs/USAGE.md 里那句丑话一直留着："本机权限模式是应用的执行审批层，不是操作系统沙箱。"

回滚也是收着做的。文件检查点默认关闭，文档写明它覆盖文件工具的写入，不覆盖任意命令和桌面应用的改动。万能 undo 很诱人，守不住那个承诺，我们就不写。

设计师上线时（v0.25.0）定了两条：默认先交可用初稿，深度走查需要你明说；模型不悄悄覆盖你刚保存的文件。这是对 agent"过度打磨"的反向约束，也是人机同改一份稿子时的底线。

还有一类活不在任何路线图上：跟模型服务商的兼容。DeepSeek 的内容审核会对包含旧工具输出的请求回 400，我们改成剥掉前序工具输出重试，更严重时把已存历史做净化，保证 Bot 不至于从此聊不动；某家兼容接口不认识 prompt cache 字段，就去掉字段重发一次并记住这个端点不支持。"随便接一个模型就能用"这句话背后全是这种活。

工程习惯从早期就定了：发布前多重校验，发布物附 SHA256SUMS 和差分更新，Mac 只在公证构建启用自动更新。9 月 19 日迁到 pnpm、建跨平台 CI（PR #23），之后 v0.27.3 到 v0.27.9 七个小版本几乎全在修打包：Mac PTY 可执行权限、ASAR 二次改写、Intel Mac 的流式测试、Windows NSIS 遇上 GitHub 500 要重试。还有一条提交把"等固定调度延迟"改成"等超时状态"，典型的 flaky test 治理。发布工程的泥泞不写在路线图上，躲不掉。

执行环境放在本地也是一次明码标价的取舍：自己的电脑加一台受管理的 QEMU Debian 虚拟机，不是云沙箱。虚拟机要 4 GB 内存和几十 GB 磁盘，建议整机 16 GB 起。换来的是文件直达本地、命令在自己机器上跑、API Key 自选可换。

## 八、适合谁

我们做 AelionBot，想解决的问题是让 AI 从问答框变成可以分工、可以交接、可以看着干活的同事。群聊加任务板分工，看得见的 Linux 桌面执行，执行账本和交付门禁把"说完成了"和"真的完成了"分开。

它适合手上真有活的人：调研报告、数据整理、原型和 PPT，或者要在自己的电脑和文件上让 AI 动手，又不想全部丢进云端。只想快速问一句话的场景不适合，为一个问题启动一台 Linux 虚拟机不划算。要求"绝对安全、绝不出错"的环境也不适合，模型审批层不是操作系统沙箱，这句话我们写在文档里，不是谦虚。

产品变得很快，这篇写的是 v0.29 时点的样子。功能砍了加、加了砍，执行诚实、信任分级、控制权留在人手里这几条从 v0.5.0 一直没松过。接下来大概还会砍掉一些现在写着的东西，希望到时候也敢写进来。
